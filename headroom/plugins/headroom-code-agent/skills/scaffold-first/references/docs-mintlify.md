# docs-mintlify scaffold-first reference (researched/verified 2026-08-22, round 8)

## Official setup commands

| Step | Command | What it generates / does |
|---|---|---|
| Install the CLI | `npm i -g mint` | Installs the **current** package. The name is `mint`, not `mintlify` — see Traps. Resolve the live version rather than pinning a number: `npm view mint version` (this reference's research run saw `4.2.819`). |
| Check the Node floor | `npm view mint engines` | npm's own registry metadata says `{ node: '>=18.0.0' }`. Mintlify's install docs recommend Node v20.17.0+, which is a stricter house-style suggestion, not the actual package floor — see the note right after this table. |
| Scaffold a new docs site (unattended) | `mint new <directory> --name "<Project> Docs" --theme <theme>` (or `--template <template>`) | Live-verified in this research run with stdin closed: it clones the `mintlify/starter` template into `<directory>` with **zero prompts** when both flags are supplied. Produces 9 items, not 6: `docs.json`, `index.mdx`, `quickstart.mdx`, `AGENTS.md`, `favicon.svg`, `logo/`, plus `.mintignore`, `LICENSE`, `README.md` — see Traps: the LICENSE and README.md describe the starter template, not your project. |
| Config file | `docs.json` (written by `mint new`) | Current config format. `mint.json` is legacy — don't scaffold or hand-write it. The schema is live and fetchable at `https://mintlify.com/docs.json`; a minimal valid file has `$schema`, `theme`, `name`, `colors.primary`, `navigation`. |
| Local preview | `mint dev` (add `--no-open` for unattended/CI use) | Long-running dev server, not a one-shot command — see Traps for backgrounding it. Serves on `http://localhost:3000` by default. |
| CI checks | `mint validate` (strict — exits nonzero on warnings/errors, includes OpenAPI validation), `mint broken-links`, `mint a11y` (aka `accessibility-check`/`a11y-check`) | These are the CI-appropriate gate commands. `mint openapi-check` is a deprecated, narrower command (validates a single OpenAPI spec file/URL) that Mintlify's own docs say to replace with `mint validate` (which validates the whole docs build, OpenAPI included, unless `--disable-openapi`) — don't wire the deprecated name into a new CI job. |
| Custom domain | `mint add-domain docs.<yourapp>.com` (optional `--basePath /docs`); requires `mint login` first | CLI path for what's otherwise a dashboard step — see Choosing and Thorough setup checklist for the DNS piece. |
| Agent-first signup | `mint signup` (flags for name/company/email, or interactive) | Pitched by Mintlify specifically for coding agents, letting them create accounts, set up a docs project, and deploy without opening a browser. Feeds into `mint new` → `mint dev` → `mint validate` → `mint add-domain`. The CLI also detects the `CLAUDECODE=1` env var Claude Code sets. |

**On the Node version contradiction:** Mintlify's own install docs recommend Node.js v20.17.0+. The npm registry's `engines` field for the `mint` package — the number npm itself enforces — says `>=18.0.0`. Both are real and both were checked live in this research; they aren't the same claim. Treat 20.17.0 as Mintlify's *recommended* baseline and 18.0.0 as the *actual floor* npm will let you install under. Match whichever your project's own Node policy already requires; don't assume the docs' recommendation is a hard install-time requirement.

(Sources: `npm view mint version`, `npm view mint engines` — both run live in this research round; https://www.mintlify.com/docs/cli/install (confirms "Node.js v20.17.0+ (LTS versions recommended)" under Prerequisites; Mintlify's docs URLs move often — if a deep link 308-redirects, follow it and trust the live page); https://www.mintlify.com/docs/quickstart; https://github.com/mintlify/starter; live scaffold run `npx --yes mint@latest new /tmp/mint-verify --name "Verify Docs" --theme mint < /dev/null`; https://mintlify.com/docs.json; https://www.mintlify.com/docs/organize/settings (documents the four required `docs.json` fields — `name`, `theme`, `colors.primary`, `navigation` — backing the Config file row above); https://www.mintlify.com/docs/cli/commands; live `mint --help` output; https://www.mintlify.com/blog/mint-signup; https://www.mintlify.com/blog/mintlify-for-terminal-agents.)

## Choosing

**Mintlify-hosted docs living in a subdirectory of the app's own repo, vs. a standalone docs repo.** Mintlify's GitHub App supports both: install it from the dashboard, and if `docs.json` isn't at repo root, toggle "docs.json is in a subdirectory" and give the relative path (e.g. `/docs`). That toggle is dashboard-only — there's no CLI or code equivalent. Putting `docs/` inside the existing app repo keeps one source of truth and one PR flow; a standalone repo is cleaner when the docs have a different audience, release cadence, or set of contributors than the app code. Neither choice is forced by the tooling — it's a project call, not a technical constraint, so surface it to Christopher rather than deciding silently.

**Deploys are Mintlify's own platform, not a user-managed Vercel project.** Once the GitHub App is installed, pushes to the default branch auto-deploy. Custom subdomain setup (dashboard's Domain Setup page, or `mint add-domain`) first requires two verification TXT records (`_acme-challenge`, `_cf-custom-hostname`) to be added and to show verified, and only then ends in a CNAME record pointing at `cname.mintlify.builders` — Mintlify's own domain, not Vercel's. Adding the CNAME before both TXT records verify commonly breaks HTTPS until provisioning finishes. It is not the user provisioning or managing a Vercel account or project, so it does not violate the house "no Vercel-managed services" rule, and there's no live evidence Mintlify's edge uses Vercel at all. The only "Vercel" mentions in Mintlify's own docs are about a different scenario — a user's own app hosted on Vercel needing a reverse-proxy rewrite to serve Mintlify docs at a subpath — unrelated to this CNAME target.

(Sources: https://www.mintlify.com/docs/deploy/github (confirms "Install the GitHub App to enable automatic deployments when you push changes", Git Settings at app.mintlify.com/settings/deployment/git-settings); https://www.mintlify.com/docs/deploy/monorepo (confirms the "docs.json is in a subdirectory" toggle and relative-path field); live `npx mint@latest add-domain --help`; https://www.mintlify.com/docs/cli/commands (mint add-domain section, fetched as markdown this audit round — prints `TXT _acme-challenge`, `TXT _cf-custom-hostname`, then `CNAME @ → cname.mintlify.builders`, with the instruction to add the TXT records first and add the CNAME only once they validate); https://www.mintlify.com/docs/customize/custom-domain (fetched live this audit round; bolded warning that switching the CNAME before both TXT records show verified commonly breaks HTTPS until provisioning finishes).)

## Never hand-write

- **The initial scaffold** (`docs.json`, `index.mdx`, `quickstart.mdx`, `AGENTS.md`, `favicon.svg`, `logo/`, `.mintignore`, `LICENSE`, `README.md` — 9 items) — comes from `mint new` / the `mintlify/starter` template. Don't type a `docs.json` skeleton from memory; it's schema-validated live against `https://mintlify.com/docs.json`, and the schema can move.
- **`llms.txt` and `llms-full.txt`** — auto-generated and hosted with zero config at `/llms.txt`, `/llms-full.txt`, and duplicated under `/.well-known/`. Optional `docs.json` fields (`description`, `markdown.instructions`, `seo.indexing`) tune the content. Only hand-author these files at the project root if you deliberately want to override the automatic ones — that's a real, supported override, not a mistake, but it should be a conscious choice.
- **`docs.json` after the scaffold exists** is the opposite case — this is expected, ordinary tuning, not something to avoid. Add navigation entries, colors, new `.mdx` pages beyond the two starter pages. The "never hand-write" rule is about not inventing the file's *shape* from scratch, not about leaving it untouched forever.

(Sources: https://mintlify.com/docs.json; https://www.mintlify.com/docs/ai/llmstxt; live scaffold output from this research run.)

## Thorough setup checklist

1. `npm i -g mint` (or run scaffolding via `npx mint@latest` without a global install).
2. `mint new docs --name "<Project> Docs" --theme <theme>` from the repo root — zero-prompt, confirmed live.
3. Tune `docs.json`: navigation, `colors.primary`, name, and any of the AI-tuning fields (`description`, `markdown.instructions`, `seo.indexing`) worth setting now.
4. `mint validate` and `mint broken-links` green **locally** before ever pushing.
5. Wire the same two commands (plus `mint a11y` if wanted) into CI, using `mint validate`'s strict nonzero exit as the gate — not the deprecated `mint openapi-check`.
6. **[Human]** Install the Mintlify GitHub App on the target repo from the dashboard (app.mintlify.com).
7. **[Human, dashboard-only]** If `docs/` lives inside an existing monorepo rather than its own repo, toggle "docs.json is in a subdirectory" and enter the relative path. No CLI/code equivalent exists for this step.
8. **[Human]** Set up the custom subdomain: either the dashboard's Domain Setup page, or `mint add-domain docs.<yourapp>.com` from an authenticated CLI session (`mint login` first). Either way, add the two verification TXT records (`_acme-challenge`, `_cf-custom-hostname`) at your DNS provider FIRST and wait until both show verified, then add the CNAME record pointing at `cname.mintlify.builders` — adding the CNAME before the TXT records verify commonly breaks HTTPS until provisioning finishes. This is a DNS-provider action outside Mintlify entirely, and, per Choosing above, not a Vercel dependency at all.
9. Confirm `mint login` has actually run once (OAuth via Stytch, opens a browser) if you want local preview search/AI-assistant features to work — otherwise expect the documented no-op (see Traps).
10. README documents the exact scaffold command, the CI gate commands, and which of steps 6–8 are still pending as human/dashboard actions.

## Traps

**`npm i -g mintlify` still works and isn't npm-flagged deprecated — but it's the old package name.** As of this check, `mintlify@4.2.819` and `mint@4.2.819` are published at the identical version, by the same `GitHub Actions` publisher, both depending on the identical `@mintlify/cli@4.0.1422` — it still tracks the same version as of this check, but Mintlify's own docs say to standardize on `mint` and uninstall `mintlify` — don't assume that parity holds going forward. (Source: https://www.mintlify.com/docs/installation; https://registry.npmjs.org/mintlify; live npm registry check in this audit round.)

**First CLI run needs outbound network access to `releases.mintlify.com`.** Without it, version resolution silently shows `client version none` rather than a hard error — worth an explicit network-reachability check in agent setup scripts before assuming a scaffold failure is something else. A historical GitHub issue on `mintlify/starter` reports the same class of failure ("requires an internet connection") as a confusing `mint dev` failure. (Sources: live CLI output in this research run; https://github.com/mintlify/starter/issues/5.)

**`mint dev` never exits on its own.** It's a long-running watch process — verified live with stdin closed and no TTY: it does not hang or block on input, it serves immediately and prints "press ctrl+c to exit" as pure status text, not something an unattended script can wait on for a clean exit code. Background it and kill it explicitly (`(mint dev --no-open < /dev/null > dev.log 2>&1 &)` plus your own teardown), or use `mint export` instead if what you actually want is a static build, not a live preview.

**Local search/AI-assistant silently no-ops without `mint login`.** `mint dev` prints "Run mint login in the cli to activate search" rather than erroring — the preview itself still renders fine unauthenticated. An agent verifying a fresh scaffold by checking whether search works could read this as a broken build when it's just unauthenticated. (Source: live test output in this research run; https://www.mintlify.com/blog/improved-cli.)

**`mint mcp` is listed in `mint --help` today but is explicitly "[Coming soon] ... run mint mcp to vote."** Mintlify pioneered `llms.txt`, so it's a reasonable but wrong assumption that they ship no MCP integration yet. There are three separate things here, easy to conflate:

1. **`mint mcp` (CLI subcommand)** — coming soon, doesn't exist today. Don't build against it.
2. **`mint index`** — installs a Mintlify index MCP server *into the coding agent itself*, for agent-side indexing of the docs. This is agent-side tooling, not a docs-site endpoint.
3. **The hosted per-site search MCP server** — already shipped, zero-config, and live today for every Mintlify docs site at the site's own `/mcp` path (and `/authed/mcp` when authenticated), discoverable at `/.well-known/mcp` and `/.well-known/mcp/server-card.json`. Confirmed live via HTTP 200 JSON responses at https://www.mintlify.com/docs/.well-known/mcp. For a docs site mounted in a subdirectory (see Choosing), these MCP discovery paths live under that mount prefix (e.g. `<mount>/mcp`, `<mount>/.well-known/mcp`), not at the domain root — mintlify.com's own bare root `/mcp` is a different, OAuth-gated admin/write MCP server proxying `mcp.mintlify.com`, not the docs-search server, so testing the literal root paths against mintlify.com itself returns 401/404. The scaffolded `AGENTS.md` (see below) even bakes a reference to this in: "Use the Mintlify docs MCP server, https://www.mintlify.com/docs/mcp".

So "no MCP-server subcommand yet" is true, but "no hosted docs-site MCP endpoint" is false — that endpoint already exists and needs no CLI command to use. (Sources: live `mint --help` output in this research run; https://www.mintlify.com/docs/ai/model-context-protocol; live HTTP checks against https://www.mintlify.com/docs/mcp and https://www.mintlify.com/docs/.well-known/mcp this audit round — mintlify.com's own docs are subdirectory-mounted at `/docs`, so the bare root `/mcp` and `/.well-known/mcp` 401/404 there, landing instead on a different, OAuth-gated admin/write MCP server; cross-checked against root-mounted docs.perplexity.ai and docs.crewai.com, both returning HTTP 200 JSON with `authentication:none` at root `/.well-known/mcp`.)

**The scaffolded `LICENSE` and `README.md` describe the starter template, not your project.** `mint new` writes 9 files, not 6 — the 6 usually cited (`docs.json`, `index.mdx`, `quickstart.mdx`, `AGENTS.md`, `favicon.svg`, `logo/`) plus `.mintignore`, `LICENSE`, and `README.md`. The `LICENSE` is MIT, "Copyright (c) 2026 Mintlify" — the starter template's own license, not a license for your project. The `README.md` describes the `mintlify/starter` template repo itself (its "Use this template" button, a link to `starter.mintlify.com/quickstart`), not your new project. Both are easy to miss because Mintlify's own `.mintignore` comment says it automatically excludes `README.md`, `LICENSE.md`, `CHANGELOG.md`, and `CONTRIBUTING.md` from doc generation — so they don't show up while you're working in the docs, but they still ship in the repo. Replace or delete them rather than shipping them as-is. (Source: live scaffold run, this audit round, `mint@4.2.819`, `npx --yes mint@latest new <dir> --name "Verify Docs R3" --theme mint < /dev/null`; file contents inspected directly.)

**`mint signup` does not return until a human clicks an emailed verification link, which can take several minutes.** The "Agent-first signup" step is pitched as flags-driven and non-interactive, and it does chain naturally into `mint new` → `mint dev` → `mint validate` → `mint add-domain` — but unlike those commands it doesn't return control on its own. `mint signup --help` states this directly: "this command does not return until the user clicks the verification link sent to their email, which can take several minutes. Non-interactive or scripted callers should run it as a background process rather than waiting on it synchronously." Running it synchronously inside an unattended scaffold script will hang the script for several minutes waiting on a human. Background it, or skip it in fully unattended flows. (Source: live `mint signup --help` output, this audit round; help text checked only, the command itself was not executed.)

**`mint openapi-check` is a deprecated, narrower command (validates a single OpenAPI spec file/URL) that Mintlify's own docs say to replace with `mint validate`** (which validates the whole docs build, OpenAPI included, unless `--disable-openapi`) — the two are not interchangeable aliases, they take different arguments and check different scopes. Wire new CI around `mint validate`, not the deprecated command name. (Source: https://www.mintlify.com/docs/cli/commands (literal note text "Use mint validate instead of the deprecated standalone mint openapi-check command"); live `npx mint@latest openapi-check --help` and `npx mint@latest validate --help` output confirming the different argument shapes and flags.)

## AI and agent resources

- **`llms.txt` / `llms-full.txt` / `.well-known/` duplicates** — auto-generated and hosted with zero config for every Mintlify docs site. Don't hand-author unless deliberately overriding (see Never hand-write). (Source: https://www.mintlify.com/docs/ai/llmstxt.)
- **`mint index`** — installs a Mintlify index MCP server into the user's own coding agent for agent-side doc indexing. Not the same thing as `mint mcp` (coming soon) or the hosted search MCP server below — see Traps for all three.
- **Hosted per-site search MCP server** — already shipped today, zero-config, at every Mintlify docs site's own `/mcp` path (and `/authed/mcp` when authenticated), discoverable at `/.well-known/mcp` and `/.well-known/mcp/server-card.json`. This is the one to point an agent at for querying a Mintlify-hosted docs site over MCP. For a docs site mounted in a subdirectory (see Choosing), these paths live under that mount prefix (e.g. `<mount>/mcp`, `<mount>/.well-known/mcp`), not at the domain root. (Source: https://www.mintlify.com/docs/ai/model-context-protocol.)
- **The starter's own `AGENTS.md`** — `mint new` scaffolds an `AGENTS.md` into the generated project as part of the `mintlify/starter` template, ready to fill in with project-specific agent guidance.
- **`npx skills add https://mintlify.com/docs`** — documented in the `mintlify/starter` repo as the way to install an AI coding-agent skill for working with the docs site.
- **`CLAUDECODE` env detection** — the CLI is documented as detecting the `CLAUDECODE=1` environment variable Claude Code sets, and is planned to adjust its own help output accordingly. Useful context if CLI behavior looks slightly different when invoked from inside Claude Code versus a plain shell.

(Sources: https://www.mintlify.com/docs/ai/llmstxt; https://www.mintlify.com/docs/ai/model-context-protocol; live `mint --help` output; https://github.com/mintlify/starter; https://www.mintlify.com/blog/mint-signup; https://www.mintlify.com/blog/mintlify-for-terminal-agents.)
