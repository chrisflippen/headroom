## Installing the SDK (the scriptable official path)

Flutter's docs push two install routes: the VS Code extension flow (interactive) and the manual SDK archive. The archive is the scriptable one. Resolve the CURRENT stable version and URL from Flutter's own release feed — never from memory:

```bash
curl -s https://storage.googleapis.com/flutter_infra_release/releases/releases_macos.json > /tmp/fr.json
python3 -c "
import json; d=json.load(open('/tmp/fr.json'))
h=d['current_release']['stable']
r=[x for x in d['releases'] if x['hash']==h and x.get('dart_sdk_arch')=='arm64'][0]
print(r['version'], d['base_url']+'/'+r['archive'])"
```

Observed this session: `3.47.2` → `.../stable/macos/flutter_macos_arm64_3.47.2-stable.zip`. Download, unzip, and put `<sdk>/bin` on PATH (persist it in `~/.zprofile` per the docs). There are equivalent `releases_linux.json` / `releases_windows.json` feeds. Homebrew's cask is not Flutter's documented path — use the archive.

Then run `flutter doctor` and read it honestly. This machine's result: Flutter ✓, Xcode ✓ (via `DEVELOPER_DIR`), Chrome ✓, Android toolchain ✗ (no Android SDK installed — Android work needs Android Studio or the command-line SDK first).

## Official setup commands

| Step | Command | What it generates |
|---|---|---|
| Scaffold an app | `flutter create <dir>` | `lib/main.dart` (the counter demo), `test/widget_test.dart`, `pubspec.yaml` + `pubspec.lock`, `analysis_options.yaml` (lints wired), and platform runners: `android/`, `ios/`, `macos/`, `linux/`, `windows/`, `web/` |
| Scope platforms | `flutter create --platforms=ios,web <dir>` | same minus unwanted runners; `--org com.example` sets the bundle/package id |
| Run on a booted iOS simulator | `flutter run -d <sim-udid>` | debug build, installs, launches, hot reload attached |
| Screenshot the running sim | `xcrun simctl io <udid> screenshot out.png` | pixel proof without any screen-recording permission |
| Test | `flutter test` | runs the scaffold's own `Counter increments smoke test` |
| Add a package | `flutter pub add <pkg>` (`dart pub add` for pure Dart) | edits `pubspec.yaml` + lockfile itself |

`flutter create` is non-interactive by default (verified, stdin closed, exit 0) — no flags needed just to keep it from prompting.

## The boot check that worked here

1. Boot a simulator: `xcrun simctl boot <udid>` (list with `xcrun simctl list devices available`).
2. `flutter run -d <udid>` in the background, logging to a file; the app is up when the log prints the hot-reload key menu and `A Dart VM Service ... is available at:`.
3. `xcrun simctl io <udid> screenshot` and LOOK at the image — this session's showed the "Flutter Demo Home Page" with the counter at 0 on the iPhone 17 simulator.
4. Interaction: `flutter test` runs the template's own widget test, which taps the `+` button and asserts the counter increments — scaffold-owned proof of the interaction loop. (For on-device E2E, `integration_test` exists but was not exercised this session.)

## Never hand-write

- `pubspec.lock` — owned by `flutter pub get`/`add`, exactly like `package-lock.json`.
- `pubspec.yaml` dependency entries — added via `flutter pub add`, not typed with guessed versions; the rest of the file (name, description, assets) is normal to edit.
- The platform runner directories (`ios/`, `android/`, `macos/`, ...) — generated by `flutter create`; regenerate a missing one with `flutter create --platforms=<p> .` in the project root rather than copying one from another repo.
- `analysis_options.yaml`'s `include: package:flutter_lints/flutter.yaml` line — scaffold-generated; add rules underneath, don't replace the include.

## Thorough setup checklist

1. Install the SDK from the release feed above; `flutter --version` then `flutter doctor` and resolve (or consciously accept) every ✗ before starting.
2. `flutter create` with `--org` and `--platforms` decided up front — retro-adding a platform works, but the org/bundle id is painful to change later.
3. Run the boot check (simulator + screenshot) before feature work.
4. `flutter test` must pass on the untouched scaffold — if it doesn't, the environment is broken, not the code.
5. Lints are already wired (`flutter_lints` via `analysis_options.yaml`); run `flutter analyze` in CI along with `flutter test`.
6. `git init` yourself and commit the scaffold's `.gitignore` and `pubspec.lock` as-is — `flutter create` does not create a repo (observed: it generates the files only).
7. Android target: requires the Android SDK — a real install step (Android Studio or cmdline-tools), not something to improvise mid-task. Surface it as a gap if the machine lacks it, as this one does.

## Traps

**A beta-only Xcode works without `sudo xcode-select` — point `DEVELOPER_DIR` at it.** This machine runs beta macOS with only `Xcode-beta.app`, and the system selection was still CommandLineTools, so `xcodebuild` failed with "requires Xcode". No sudo available to an agent. Fix that worked for every Xcode-touching command this session (flutter run, simctl, pod install): `export DEVELOPER_DIR=/Applications/Xcode-beta.app/Contents/Developer`. The permanent fix is the user running `sudo xcode-select -s <that path>` — ask, don't wait. (Recorded run: 2026-08-30, Xcode 27.0 beta. Later that same day the user installed and selected a full release Xcode 26.6 on this machine, so the override is now the fallback for beta-only machines, not this machine's current state.)

**The first iOS debug build is minutes of near-silence after "Launching lib/main.dart".** Not a hang; the log file eventually prints the Dart VM Service line. Poll the log, don't kill it. (Recorded run: 2026-08-30.)

**`flutter doctor`'s Android ✗ does not block iOS/web/desktop work.** Don't install half an Android toolchain reflexively to clear the checkmark; note it and move on unless Android is actually a target. (Recorded run: 2026-08-30.)
