# python-web scaffold-first reference (researched 2026-08-21, round 5)

Covers FastAPI and Django specifically — the two web frameworks in this platform's
stack. This page assumes the base `python-uv.md` reference for generic uv mechanics
(`uv init`, `uv add`, `pyrefly init`, pre-commit, dependency groups); it does not
repeat that material, only what's different once a web framework is in the mix.

## Official setup commands

| Step | Command | What it generates |
|---|---|---|
| Start a new FastAPI project | `uv init --no-package` (flat layout — see Choosing) | `pyproject.toml`, `.python-version`, `.gitignore`, `README.md`, git repo, `main.py` |
| Add FastAPI + its dev tooling | `uv add fastapi --extra standard` (equivalent: `uv add "fastapi[standard]"`) | adds `fastapi`, and pulls in `uvicorn[standard]`, `fastapi-cli[standard]`, `httpx`, `jinja2`, `python-multipart`, `email-validator` as transitive deps; edits `pyproject.toml`, `uv.lock`, syncs `.venv` |
| Run the FastAPI dev server | `uv run fastapi dev [path]` | no files — starts uvicorn with reload on `127.0.0.1`, auto-detecting the app object |
| Run the FastAPI prod server | `uv run fastapi run [path]` | no files — starts uvicorn without reload on `0.0.0.0` |
| FastAPI project scaffold beyond a blank app | **no CLI command exists.** The [official full-stack template](https://github.com/fastapi/full-stack-fastapi-template) (FastAPI + SQLModel + Postgres backend, React + Vite + TypeScript frontend, Docker Compose, Traefik, GitHub Actions) is generated by clicking **"Use this template"** on GitHub — there is no `copier`, `cookiecutter`, or CLI equivalent documented. Treat "start from `uv init` + `uv add fastapi` and optionally clone/template that repo" as the honest answer, not a missing feature on your part. |
| Start a new Django project | `uv init --app --no-package` (flat layout), then `uv add django`, then `uv run django-admin startproject <config-name> .` | `pyproject.toml` etc. from uv, then from Django: `manage.py`, `<config-name>/settings.py`, `<config-name>/urls.py`, `<config-name>/asgi.py`, `<config-name>/wsgi.py`, `<config-name>/__init__.py` |
| Add a Django app | `uv run manage.py startapp <app-name>` (once `manage.py` exists; use `django-admin startapp` only before a project exists) | `<app-name>/models.py`, `admin.py`, `apps.py`, `tests.py`, `views.py`, `migrations/__init__.py`, `<app-name>/__init__.py` |
| Django migrations | `uv run manage.py makemigrations`, `uv run manage.py migrate` | files in `<app>/migrations/`; applies schema to the configured DB |
| Django dev server | `uv run manage.py runserver` | no files |
| Type-check config (both frameworks) | `uv run pyrefly init --non-interactive` (after `uv add --dev pyrefly`) | `pyrefly.toml` — see `python-uv.md` |
| Django type stubs | `uv add --dev "django-stubs[compatible-mypy]"` | edits `pyproject.toml`/`uv.lock`; add `django_settings_module` under `[tool.django-stubs]` by hand (pyrefly/pyright/ty read the stub package directly — no mypy plugin step needed for them) |
| Test runner + async test support (both) | `uv add --dev pytest pytest-asyncio` | edits `pyproject.toml` `[dependency-groups].dev` |
| Async HTTP test client (both) | `uv add --dev httpx` (already a transitive dep of `fastapi[standard]`; Django doesn't pull it in, so add it explicitly for Django) | edits `pyproject.toml`/`uv.lock` |

**No init command exists for `pytest`, `pytest-asyncio`, or `ruff` here either** — same situation as the base uv reference: hand-write the `[tool.pytest.ini_options]` and `[tool.ruff]` blocks in `pyproject.toml`, there's no generator to defer to for either framework.

## Choosing

**FastAPI: `uv init --no-package` (flat), not the packaged default.** Since uv 0.12, a bare `uv init` (or `uv init --app`) produces a *packaged* layout — code lives in `src/<name>/__init__.py`. Verified on this machine: `fastapi dev` and `fastapi run` autodetect the app object by trying, in order, `main.py`, `app.py`, `api.py`, `app/main.py`, `app/app.py`, `app/api.py` (exact list from `fastapi dev --help` on fastapi-cli, run today) — none of those paths point into `src/<name>/`. Run the packaged layout unmodified and `fastapi dev` fails with "Could not find a default file to run" (reproduced on this machine). You have two correct options, not one: either `uv init --no-package` for the flat `main.py` layout the CLI expects out of the box — this is also exactly what [Astral's own official uv+FastAPI guide](https://docs.astral.sh/uv/guides/integration/fastapi/index.md) uses (`uv init --no-package` → `uv add fastapi --extra standard` → `uv run fastapi dev`) — or keep the packaged layout and add `[tool.fastapi] entrypoint = "<pkgname>:app"` to `pyproject.toml` (documented at https://fastapi.tiangolo.com/fastapi-cli/, confirmed working on this machine against a `src/`-layout project). Pick packaged+entrypoint only if the project already needs to be an installable/publishable package for another reason; otherwise the flat layout needs zero extra config.

**Django: also `--no-package`, for a different reason.** `django-admin startproject` builds its own package (`<config-name>/settings.py` etc.) and its own root-level entry point (`manage.py`). If you run plain `uv init --app` first, you get an unused, empty `src/<name>/__init__.py` sitting next to Django's real `<config-name>/` package — confirmed on this machine, `manage.py check` still passes but the `src/` package is dead weight nothing imports. `uv init --app --no-package` avoids creating it in the first place.

**`fastapi[standard]` vs bare `fastapi`.** `[standard]` is what FastAPI's own docs lead with (`uv add "fastapi[standard]"`) and what Astral's guide uses too (`uv add fastapi --extra standard` — identical result, different flag syntax). It pulls `uvicorn[standard]` (the dev/prod server), `fastapi-cli[standard]` (the `fastapi` command itself), `httpx` (needed by `TestClient`), `jinja2`, and `python-multipart`. Skip it only for a pure library or a deployment that brings its own ASGI server and doesn't need the CLI — bare `fastapi` has none of those.

**pytest-asyncio: `auto` mode, not `strict`.** `strict` (pytest-asyncio's actual current default per its own docs and confirmed via `pytest --help` on this machine) requires an explicit `@pytest.mark.asyncio` on every async test. `auto` mode runs all `async def test_*` functions without the marker and is what pytest-asyncio's own docs call "the recommended default" for a project that only uses asyncio (not trio). Set `asyncio_mode = "auto"` under `[tool.pytest.ini_options]` unless something else in the stack needs strict opt-in per test.

**pytest-asyncio vs anyio for FastAPI tests — know both, don't blend them by accident.** FastAPI's own "Async Tests" doc page uses the `anyio` pytest plugin (`@pytest.mark.anyio`), not pytest-asyncio — that's a different plugin with its own config surface. This repo's stack (per its dependency digest) uses pytest-asyncio, so use `@pytest.mark.asyncio` (or `asyncio_mode = "auto"` and skip the marker) consistently — don't copy the `@pytest.mark.anyio` snippet from FastAPI's docs verbatim into a pytest-asyncio-configured suite; the two markers are not interchangeable and mixing them silently skips tests instead of failing loudly.

**Ruff rule selection: turn on the framework-specific sets explicitly, they're opt-in.** Ruff ships a `DJ` (flake8-django) rule set for Django — `DJ001`, `DJ003`, `DJ006`, `DJ007`, `DJ008`, `DJ012`, `DJ013` (https://docs.astral.sh/ruff/rules/#flake8-django-dj; gaps in the numbering are Ruff's own reservation, not an omission here) — and a `FAST` set for FastAPI — `FAST001` (redundant `response_model`), `FAST002` (dependency not wrapped in `Annotated`), `FAST003` (path parameter missing from the function signature), all stable with autofixes (https://docs.astral.sh/ruff/rules/#fastapi-fast). Neither is in Ruff's default rule set; add `"DJ"` or `"FAST"` to `select` in `[tool.ruff.lint]` explicitly. Verified on this machine: `ruff check .` with `select = ["E", "F", "I", "FAST"]` passes clean on a fresh FastAPI app; `select = ["E", "F", "I", "DJ"]` on a fresh `startapp` output correctly flags the unused `render` import Django's own template leaves in `views.py` — that's Ruff doing its job on Django's own scaffold, not a bug in either tool.

**django-stubs: install it, but don't expect a full mypy-plugin experience outside mypy.** `django-stubs[compatible-mypy]` (https://github.com/typeddjango/django-stubs) is the standard source of Django type stubs. It documents "basic support, CI-checked" for pyright, pyrefly, and ty — those checkers read the stub package directly since none of them support mypy's plugin architecture; mypy alone gets the full plugin (`mypy_django_plugin.main` + `django_settings_module` in `[tool.django-stubs]`). Since this reference standardizes on pyrefly, install the stubs for the coverage they give but don't expect mypy-plugin-grade inference on dynamic Django patterns (e.g. reverse relations, manager return types) — that gap is real and documented by the stub project itself, not a local misconfiguration.

## Never hand-write

- `<config-name>/settings.py`, `urls.py`, `asgi.py`, `wsgi.py`, `manage.py` — from `django-admin startproject`
- `<app-name>/models.py`, `admin.py`, `apps.py`, `views.py`, `tests.py`, `migrations/__init__.py` — from `manage.py startapp`
- `<app>/migrations/*.py` migration files — from `manage.py makemigrations`, never written from scratch (same rule as Alembic in `python-uv.md`)
- `main.py`'s FastAPI app skeleton isn't generated by anything — FastAPI has no scaffold command, so a hand-written `FastAPI()` instantiation and route are the correct starting point, not a violation
- `[tool.fastapi]` entrypoint line — this one line is meant to be hand-added; nothing generates it, `fastapi-cli`'s own docs show it as something you type
- `pyrefly.toml`, `[tool.django-stubs]`'s `django_settings_module` value — same rule as the base uv reference: let `pyrefly init` write the file, hand-edit only the specific settings it leaves open

## Thorough setup checklist

1. Pick flat vs packaged per the Choosing section above — for FastAPI or Django, default to `uv init --app --no-package` (or `uv init --no-package` for FastAPI-only) unless the project needs to be installable as a package
2. `uv add fastapi --extra standard` (FastAPI) or `uv add django` (Django) — resolve current versions via `uv add`, don't hardcode a remembered version
3. Django only: `uv run django-admin startproject <config-name> .`, then `uv run manage.py startapp <app-name>` for each app, add the app to `INSTALLED_APPS`
4. FastAPI only: if using the packaged layout, add `[tool.fastapi] entrypoint = "<pkg>:app"` to `pyproject.toml`
5. `uv add --dev pytest pytest-asyncio` (both); Django additionally needs `uv add --dev httpx` explicitly (FastAPI already has it transitively via `[standard]`)
6. `asyncio_mode = "auto"` under `[tool.pytest.ini_options]`
7. FastAPI: write tests against `httpx.AsyncClient(transport=ASGITransport(app=app), base_url=...)` for async coverage, or `fastapi.testclient.TestClient` for sync — if using `TestClient`, `uv add --dev httpx2` too (see Traps)
8. Django: write tests against `httpx.AsyncClient(transport=ASGITransport(app=get_asgi_application()), base_url="http://localhost")` — not `"http://test"` (see Traps) — or fall back to Django's own `django.test.AsyncClient` if you don't want the httpx dependency for Django tests at all
9. `uv add --dev ruff pyrefly`; select `["E", "F", "I", "FAST"]` for FastAPI or `["E", "F", "I", "DJ"]` for Django in `[tool.ruff.lint]`, on top of whatever house rules the project already runs
10. `uv add --dev "django-stubs[compatible-mypy]"` for Django projects; set `django_settings_module` in `[tool.django-stubs]`
11. `uv run pyrefly init --non-interactive`, confirm `pyrefly check` is clean or has reviewed suppressions
12. Django: `uv run manage.py migrate` before first run, `uv run manage.py check` as a fast unattended smoke test
13. README documents the exact `uv run fastapi dev` / `uv run manage.py runserver` command to bring the app up from a clean clone

## Traps

**`fastapi.testclient.TestClient` silently prefers a package called `httpx2` over `httpx`, and warns if it can't find it — verified on this machine today, not in any doc yet.** Starlette 1.6.0's `testclient.py` (the module `fastapi.testclient.TestClient` re-exports) does `import httpx2 as httpx`, falling back to plain `httpx` only if `httpx2` isn't installed, and issues `StarletteDeprecationWarning: Using httpx with starlette.testclient is deprecated; install httpx2 instead` on the fallback path. Confirmed by reading the installed `starlette/testclient.py` source directly and by reproducing the warning on a fresh `uv add "fastapi[standard]"` project (`fastapi[standard]` pulls plain `httpx`, not `httpx2`, as of today). `httpx2` (PyPI, 2.12.0, released 2026-08-18 — three days before this research) is a from-scratch continuation of `httpx` published under Pydantic Services Inc's stewardship; it exposes the same `Client`/`AsyncClient`/`ASGITransport` API surface, confirmed by installing it here. Practical effect: if the test suite uses `fastapi.testclient.TestClient` (FastAPI's own tutorial's headline recommendation), `uv add --dev httpx2` to silence the warning and stay on the maintained path; if it only uses `httpx.AsyncClient` + `ASGITransport` directly (bypassing `starlette.testclient` entirely — FastAPI's own async-tests pattern), no warning fires either way, plain `httpx` is untouched by this. This is exactly the kind of fact that will not be in training data — re-verify this specific claim (`uv add httpx2`, check for the warning) before trusting it on a later date; a library-level rename this fresh can also reverse or get walked back. (Source: direct inspection of `starlette/testclient.py` in a `uv add "fastapi[standard]"` install, and `uv add --dev httpx2` on this machine, 2026-08-21.)

**Django rejects the `base_url` FastAPI's own docs use for `httpx.AsyncClient` testing.** FastAPI's async-tests example uses `base_url="http://test"`; pointed at a Django ASGI app instead of a Starlette one, this fails with `django.core.exceptions.DisallowedHost: Invalid HTTP_HOST header: 'test'` — reproduced on this machine against a fresh `startproject` with its default `ALLOWED_HOSTS = []` and `DEBUG = True`. Django's `ALLOWED_HOSTS` check runs on every request and, unlike Starlette, isn't bypassed for test traffic unless something (Django's own test runner, or `pytest-django`) adds `"testserver"` to it first — plain `pytest` + `httpx` does neither. Fix verified on this machine: use `base_url="http://localhost"` (always allowed when `DEBUG=True`, regardless of `ALLOWED_HOSTS`), or add `"testserver"` to `ALLOWED_HOSTS` by hand to match Django's own test-client convention.

**`uv init --app`'s packaged default silently breaks `fastapi dev`/`fastapi run` autodetection.** Reproduced on this machine: a fresh packaged project (`uv init --app`, code in `src/<name>/__init__.py`) with `fastapi[standard]` added gives `Could not find a default file to run` from `fastapi dev` with no other changes — the six autodetected paths never look inside `src/`. This is a straightforward consequence of two independently-reasonable defaults (uv's packaged-by-default since v0.12, documented in `python-uv.md`; fastapi-cli's fixed autodetect list) colliding, not a bug in either tool. Fix is `--no-package` at init time or the `[tool.fastapi] entrypoint` line — see Choosing above.

**There is no `fastapi new`, `fastapi init`, `copier`, or `cookiecutter` command for the official full-stack template.** `fastapi --help` on this machine lists exactly five subcommands: `dev`, `run`, `deploy`, `login`, `cloud` — no scaffold/init/new. The [full-stack-fastapi-template repo](https://github.com/fastapi/full-stack-fastapi-template) is generated only by clicking GitHub's "Use this template" button (confirmed by reading the repo's own README) — an agent cannot run this unattended from a CLI; it needs a human on github.com, or a manual `git clone` of the template repo as a substitute (not the same as GitHub's templating, which decouples git history).

**Django's official docs never mention pytest.** Confirmed by reading `docs.djangoproject.com`'s testing-tools page directly: it documents only `django.test.Client`, `django.test.AsyncClient`, `RequestFactory`, and the `unittest`-based `TestCase`/`TransactionTestCase`/`SimpleTestCase`/`LiveServerTestCase` classes — zero mentions of `pytest`, `pytest-django`, or `httpx`. If a project wants pytest to drive Django tests the way it drives FastAPI tests (fixtures, `-k` filtering, one runner for both frameworks), that requires `pytest-django` as an additional, separate dependency — it is not in this repo's current dependency digest and is not covered by this page; don't assume `pytest` alone gets Django's ORM/DB fixtures working the way it does for a stateless FastAPI app.

## AI and agent resources

**Astral (uv's own maintainer) publishes an official FastAPI integration guide** at `https://docs.astral.sh/uv/guides/integration/fastapi/index.md` — a first-party (not FastAPI-authored) walkthrough of `uv init --no-package` → `uv add fastapi --extra standard` → `uv run fastapi dev`, confirmed by fetching it directly. It's listed in uv's own `llms.txt` (`https://docs.astral.sh/uv/llms.txt`, already documented in `python-uv.md`) under the Integrations section — fetch that index first, same as any other uv doc lookup. No equivalent Astral guide exists for Django (checked the same `llms.txt` — not listed).

**Neither FastAPI nor Django publishes an `llms.txt`.** Checked `https://fastapi.tiangolo.com/llms.txt` (404) and `https://docs.djangoproject.com/en/stable/llms.txt` (404, and the bare-domain variant just redirects to the normal docs homepage rather than serving a real llms.txt). Don't assume one exists for either framework's own docs site — fall back to Context7 or a direct docs fetch, same guidance the base uv reference gives for pytest and Alembic.

**No official MCP server for either framework, and no `AGENTS.md` convention in either project's source repo.** Checked `github.com/fastapi/fastapi` and `github.com/django/django` for a repo-root `AGENTS.md` — neither exists (404 on both). Community MCP wrappers exist for both ecosystems (e.g. unofficial "fastapi-mcp" packages), but nothing first-party — don't cite a community wrapper as if FastAPI or Django endorsed it.

**Astral's own Claude Code plugin covers the shared tooling, not the frameworks.** `astral-sh/claude-code-plugins` (already documented in `python-uv.md`) gives `/astral:uv`, `/astral:ruff`, `/astral:ty` skills — genuinely useful on a FastAPI or Django project since both run on this same uv/Ruff base, but it has no FastAPI- or Django-specific skill inside it; don't expect framework-aware guidance from it beyond what the base toolchain already provides.
