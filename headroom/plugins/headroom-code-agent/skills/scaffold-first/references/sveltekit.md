# SvelteKit setup reference (verified 2026-08-21, round 8)

This covers the `sv` CLI, SvelteKit configuration (written into `vite.config.ts`'s `sveltekit()` plugin call by default, or `svelte.config.js` for a project that already has one), deployment adapters, `svelte-check`, and the standard project layout. Everything below is pulled straight from the official Svelte docs (svelte.dev/docs/cli, svelte.dev/docs/kit, and svelte.dev/docs/ai), read live, not from memory.

## Official setup commands

Run these with `npx` (or your package manager's equivalent, e.g. `pnpm dlx`, `bunx`). If `sv` is already installed locally in the project, the same commands use that local copy. `<pm>` means whatever package manager `sv` currently recognizes for `--install` — as of sv 0.17.0 that's `npm`, `yarn`, `pnpm`, `pnpm-rush`, `bun`, `deno`, `nub`, and `aube`; the CLI adds new ones over time, so check `sv add --help` rather than hardcoding the list. (Source: `npx sv add --help` / `npx sv create --help` run on this machine, sv@0.17.0; svelte.dev's own CLI docs pages still list only the old five, so the live `--help` output is the authority here.)

| Command | What it does |
|---|---|
| `npx sv create [path] [--template <minimal\|demo\|library>] [--types <ts\|jsdoc>] [--no-add-ons \| --add <list>] [--install <pm> \| --no-install]` | Scaffolds a brand-new SvelteKit project. Run bare and it prompts for everything: a template, TypeScript vs JSDoc typing, which add-ons to install, and confirmation before installing dependencies. For an agent or a script, pass the flags to skip every prompt — `--no-add-ons` (or `--add <list>`) skips the add-ons picker, and `--install <pm>` or `--no-install` skips the install prompt. Generates `package.json`, `vite.config.ts` (with SvelteKit config, including the adapter, passed straight to the `sveltekit()` plugin call), `tsconfig.json`/`jsconfig.json`, `src/` (with `routes/`, `lib/`, `app.html`), `static/`, and `.gitignore`/`.npmrc`. No `svelte.config.js` is generated by default — current `sv create` output keeps SvelteKit config inside `vite.config.ts` and ignores a `svelte.config.js` if one happens to exist. (Source: svelte.dev/docs/kit/configuration, svelte.dev/docs/cli/sv-utils.) |
| `npx sv create --template minimal --types ts --no-add-ons --no-install my-app` | Fully non-interactive: barebones template, TypeScript typing, no add-ons prompt, no install prompt. `--template` and `--types` alone do **not** suppress the add-ons or install prompts — you still need `--no-add-ons` (or `--add <list>`) and `--install <pm>`/`--no-install`, or the CLI stops and waits for input. (Source: svelte.dev/docs/cli/sv-create — Options: --no-add-ons, --install/--no-install) |
| `npx sv create --add eslint prettier vitest playwright --install <pm> [path]` | Scaffold a new project and install specific add-ons in one pass, skipping the interactive add-ons prompt. Still needs `--install <pm>` (or `--no-install`), or it stops to ask which package manager to use. (Source: svelte.dev/docs/cli/sv-create — Options: --install/--no-install) |
| `npx sv add <add-on> [add-on...] --install <pm>` | Adds official tooling to an **existing** project. Passing explicit add-on names skips the interactive add-ons picker; passing `--install <pm>` (or `--no-install`) skips the install prompt. Run with no args and no flags for the interactive picker instead. Official add-ons: `eslint`, `prettier`, `vitest`, `playwright`, `sveltekit-adapter`, `tailwindcss`, `drizzle`, `mdsvex`, `paraglide`, `storybook`, `better-auth`, `ai-tools`. (Source: svelte.dev/docs/cli/sv-add) |
| `npx sv add sveltekit-adapter="adapter:node" --install <pm>` | Installs and wires up a specific deployment adapter (`auto`, `node`, `static`, `vercel`, `cloudflare`, `netlify`) directly into `vite.config.ts`'s `sveltekit()` plugin call — current `sv`-created projects have no `svelte.config.js`, so that's where the adapter import and options land. If the project already has a `svelte.config.js` (e.g. from an older scaffold), the add-on writes there instead. Needs `--install <pm>` (or `--no-install`), or it stops to ask about installing dependencies. (Source: svelte.dev/docs/cli/sv-add — Options: --install/--no-install; svelte.dev/docs/kit/configuration; svelte.dev/docs/cli/sv-utils) |
| `npx sv add eslint --install <pm>` | Installs `eslint-plugin-svelte` + friends, writes `eslint.config.js`, updates `.vscode/extensions.json`, and wires in Prettier/TypeScript support if those are already present. Needs `--install <pm>` (or `--no-install`) to run unattended. |
| `npx sv add prettier --install <pm>` | Adds Prettier scripts to `package.json`, writes `.prettierrc` and `.prettierignore`, and updates the ESLint config if present. Needs `--install <pm>` (or `--no-install`) to run unattended. |
| `npx sv add vitest="usages:unit,component" --install <pm>` | Installs Vitest, adds test scripts to `package.json`, wires a client/server-aware test setup into the Vite config, and drops in demo tests. Needs `--install <pm>` (or `--no-install`) to run unattended. |
| `npx sv add playwright --install <pm>` | Installs Playwright, adds scripts to `package.json`, writes a Playwright config file, updates `.gitignore`, and adds a demo test in `tests/`. Needs `--install <pm>` (or `--no-install`) to run unattended. |
| `npx sv check` (needs `svelte-check` installed as a dev dependency) | Runs `svelte-check`: TypeScript/JS compiler errors, unused CSS, accessibility warnings, across `.svelte`, `.ts`, and `.js` files. Runs unattended as-is. |
| `npx sv migrate [migration]` | Runs codemods for version upgrades: `svelte-5`, `sveltekit-2`, `svelte-4`, `app-state` ($app/stores → $app/state), `self-closing-tags`, `package` (svelte-package v1→v2), `routes`. Pass the migration name explicitly — omitting it opens an interactive picker, the same way `sv add` does with no add-on names. (Source: svelte.dev/docs/cli/sv-migrate) |
| `svelte-kit sync` | Regenerates `tsconfig.json`'s base config and the `./$types` route types. Runs automatically as the npm `prepare` script and on `dev`/`build` — you should almost never need to run it by hand. |

## Choosing

**Project template (`sv create --template`).** `minimal` is the right default for almost everything — it's the barebones scaffold. Pick `demo` only when you want a working example (a word-guessing game) to learn from or tear apart. Pick `library` when the whole point of the repo is to publish a Svelte component package via `svelte-package` — it sets up packaging from day one instead of a normal app. A fourth choice, `addon`, exists in the live CLI but not on the docs page: it scaffolds a community `sv` add-on package (not an app) and interactively prompts for an npm org name, so agents should not reach for it when creating an application. (Source: `npx sv create --help` on sv@0.17.0, run on this machine; svelte.dev/docs/cli/sv-create documents only the first three as of 2026-08-21.)

**TypeScript vs JSDoc (`--types`).** Use `ts` unless you have a specific reason not to — it's the default expectation in the Svelte ecosystem and every official add-on assumes it's there. `jsdoc` exists for people who want type-checking without a build-time TS step; pick it only if you already have a JSDoc-based codebase you're extending. `--no-types` is explicitly discouraged by the docs themselves ("Not recommended!") — never choose it for a new project.

**Deployment adapter (`sv add sveltekit-adapter`).** `auto` is a fine placeholder while you haven't picked a host — it detects common platforms at build time but is less configurable. Once you know where you're deploying, swap to the specific adapter: `node` for a self-hosted or containerized server you run yourself, `static` when the whole site can be prerendered (SSG, no server-side logic at request time), and `vercel`/`cloudflare`/`netlify` when you're deploying to that platform and want its platform-specific features (ISR, edge functions, etc.) available. Don't ship on `auto` — the docs frame it as a bootstrapping convenience, not a production choice. The adapter itself now lives in `vite.config.ts`'s `sveltekit()` plugin call for current scaffolds, not a separate `svelte.config.js` (see the setup table above) — swapping adapters means changing that call, unless the project is one of the older ones that still has a `svelte.config.js`.

**Testing add-on: Vitest vs Playwright.** These aren't competitors — they answer different questions. `sv add vitest` (with `usages:unit,component`) is for fast, in-process unit and component tests. `sv add playwright` is for real-browser end-to-end tests that click through actual pages. Most projects that take testing seriously add both; pick just Vitest if you only need logic-level coverage, and add Playwright once you have user flows worth protecting end-to-end.

**Local MCP vs remote MCP for agent tooling.** Local (`npx -y @sveltejs/mcp`, or `claude mcp add -t stdio ...`) runs on the machine doing the coding — no network dependency, but every client needs its own one-time setup. Remote (`https://mcp.svelte.dev/mcp`) needs zero local install and the Svelte team states it does not log, store, or inspect the code sent to it — reach for it when you can't or don't want to install anything locally, or when you're standing up a hosted agent (e.g. GitHub Coding Agent) that can't run a local process at all.

**Plugin bundle vs individual AI tools (`sv add ai-tools`).** If your agent client is Claude Code or OpenCode, take the bundled plugin (`delivery:plugin` — no option has a default here, you must pass it explicitly, same as `ide`/`tools`/`mcpSetup`) — it wires up the MCP server, the two skills, and the `svelte-file-editor` subagent together and keeps itself updated. Plugin delivery is only available for Claude Code and OpenCode; Codex CLI and GitHub Copilot CLI aren't named `ide` choices at all (they fall under `other`) and must use `delivery:tools` instead. (Source: svelte.dev/docs/cli/ai-tools; `npx sv add --help` run on this machine, sv@0.17.0.) Fall back to individual tools (`delivery:tools`, picking from `mcp`, `svelte-code-writer`, `svelte-core-bestpractices`, `svelte-file-editor`) only for clients without plugin support, or when you deliberately want to hand-pick which pieces to install. If you pick `delivery:tools` with `tools:mcp`, also pass `mcpSetup:local` or `mcpSetup:remote` in the same option string — the add-on needs that choice too and stops to ask for it interactively otherwise, the same way `ide`, `delivery`, and `tools` do. (Source: `npx sv add --help`, and `npx sv add ai-tools="ide:claude-code+delivery:tools+tools:mcp"` reproducing the interactive prompt, both run on this machine.)

## Never hand-write

Two different rules apply here, and they are not the same thing:

**A. Files a generator produces — run the generator, don't type these out from memory.** Once generated they are normal source files you keep editing by hand as the project evolves:
- The adapter block inside `vite.config.ts`'s `sveltekit()` plugin call (or inside `svelte.config.js`, for a project that already has one) — use `npx sv add sveltekit-adapter`
- `eslint.config.js` — use `npx sv add eslint`
- `.prettierrc`, `.prettierignore` — use `npx sv add prettier`
- Playwright config (`playwright.config.ts`) — use `npx sv add playwright`
- Vitest wiring in `vite.config.ts` — use `npx sv add vitest`
- `tsconfig.json` / `jsconfig.json` (top level) — created by `npx sv create` with your chosen `--types` option

**B. Files that are truly machine-generated output — never hand-edit these, ever, even after they exist:**
- The entire `.svelte-kit/` directory (configurable via `outDir`) — safe to delete anytime, SvelteKit regenerates it on `dev`/`build`
- `.svelte-kit/tsconfig.json` — the base config your root `tsconfig.json` `extends`; change top-level options like `include`/`exclude` in your own `tsconfig.json`, never in the generated one
- Generated route types imported as `./$types` — these come from `svelte-kit sync` reading your route files, not from anything you write

## Thorough setup checklist

A properly scaffolded SvelteKit repo has, before any feature work starts:

- [ ] Project created with `npx sv create` (not hand-copied from another repo or written from a blog post)
- [ ] A deliberate choice of TypeScript vs JSDoc typing made at creation time (`--types ts` or `--types jsdoc`), not left to `--no-types`
- [ ] A deployment adapter installed via `npx sv add sveltekit-adapter` matching the actual target platform (`node`, `static`, `vercel`, `cloudflare`, `netlify`) — `adapter-auto` is fine for "not decided yet" but should be swapped for the real one before shipping
- [ ] `eslint.config.js` present via `npx sv add eslint`
- [ ] Prettier present via `npx sv add prettier` (keeps ESLint and Prettier from fighting each other, since the add-on wires them together)
- [ ] A test setup that matches what the project actually needs: `npx sv add vitest` for unit/component tests, `npx sv add playwright` for browser/e2e tests — added at scaffold time, not bolted on later by hand
- [ ] `svelte-check` (`npx sv check`) runs clean, or its failures are understood and tracked, before merging
- [ ] `package.json` has `"type": "module"` and lists `@sveltejs/kit`, `svelte`, and `vite` as devDependencies (this happens automatically from `sv create` — verify it wasn't stripped by a manual edit)
- [ ] Standard structure respected: routes in `src/routes`, shared code in `src/lib` (server-only code in `src/lib/server`), static assets in `static/`, tests in `tests/` (Playwright) or alongside source as `*.test.js` (Vitest)
- [ ] `.svelte-kit/` is in `.gitignore` and nobody has committed it or hand-edited files inside it
- [ ] Any unattended `sv create`/`sv add` call in scripts or agent workflows passes `--no-add-ons` (or `--add <list>`) and `--install <pm>` (or `--no-install`) — the default is to stop and prompt

## Traps

**Interactive prompts fire by default, and on closed/non-interactive stdin they don't hang or error — they silently exit 0 having done nothing.** `sv create` shows an add-ons picker unless you pass `--no-add-ons` (or explicit `--add ...`), and both `sv create` and `sv add` prompt to install dependencies unless you pass `--install <pm>` or `--no-install` — the docs describe these flags precisely because the prompts are the default behavior, not an edge case. Verified on this machine (sv@0.17.0): running `npx sv create --template minimal --types ts . < /dev/null` in an empty directory prints the add-ons picker, then exits with code 0 and writes zero files — no project is scaffolded, and nothing about the exit code signals that. The same happens with a bare `npx sv add < /dev/null` inside an existing project: it prints the picker and exits 0 with no changes made. A script or agent that only checks `$?` will read either of these as success. That flag pair also doesn't catch every prompt an add-on can raise on its own: `sv add ai-tools="ide:claude-code+delivery:tools+tools:mcp"` still stops and asks "Which MCP setup would you like to use? Local / Remote" unless you also pass `mcpSetup:local` or `mcpSetup:remote` in the option string — neither `--no-add-ons` nor `--install`/`--no-install` suppresses it. (Source: svelte.dev/docs/cli/sv-create, svelte.dev/docs/cli/sv-add — Options sections; `npx sv create --template minimal --types ts . < /dev/null`, `npx sv add < /dev/null`, `npx sv add --help`, and `npx sv add ai-tools="ide:claude-code+delivery:tools+tools:mcp"` all run on this machine, sv@0.17.0.)

**Hand-writing `eslint.config.js` or a Playwright/Vitest config from memory** instead of running `npx sv add eslint` / `npx sv add playwright` / `npx sv add vitest`. This produces configs that don't match the current plugin APIs and skips steps the add-on does automatically, like updating `.vscode/extensions.json` or cross-wiring ESLint and Prettier. (Source: svelte.dev/docs/cli/eslint, svelte.dev/docs/cli/prettier, svelte.dev/docs/cli/vitest, svelte.dev/docs/cli/playwright.)

**Hand-edits to `.svelte-kit/tsconfig.json` get silently wiped.** `svelte-kit sync` regenerates the whole `.svelte-kit/` directory, including its `tsconfig.json`, every time it runs — and it runs automatically as the npm `prepare` script and on `dev`/`build`. Any manual fix placed there disappears on the next run with no warning; the fix belongs in the project's own `tsconfig.json`, which `extends` the generated one. (Source: svelte.dev/docs/kit/project-structure.)

**Manually writing `./$types` imports or fabricating the shape of generated route types**, rather than running `svelte-kit sync` (or just running `dev`, which does it automatically) and importing what's actually generated. (Source: svelte.dev/docs/kit/cli.)

**Skipping `npx sv add sveltekit-adapter` and hand-editing the adapter import in `vite.config.ts`'s `sveltekit()` plugin call** (or whichever config file the project actually has — an older project may still keep it in `svelte.config.js`) with a guessed package name/options. Adapter APIs and option names change between versions; the add-on installs the matching package version and correct option shape together. (Source: svelte.dev/docs/cli/sveltekit-adapter, svelte.dev/docs/cli/sv-add; svelte.dev/docs/kit/configuration; svelte.dev/docs/cli/sv-utils.)

**Community `sv add` add-ons are unreviewed and can run malicious code.** The `--no-download-check` flag exists to suppress a warning the CLI shows specifically because "Svelte maintainers have not reviewed community add-ons for malicious code" — treat any non-official add-on (anything outside `ai-tools`, `better-auth`, `drizzle`, `eslint`, `experimental`, `mdsvex`, `paraglide`, `playwright`, `prettier`, `storybook`, `sveltekit-adapter`, `tailwindcss`, `vitest`) as untrusted supply chain until reviewed. (Source: svelte.dev/docs/cli/sv-add; `npx sv add --help` run on this machine, sv@0.17.0, lists `experimental` under the same "Official Add-Ons:" heading as the other twelve — it configures SvelteKit experimental flags and pre-release versions and is documented as first-party at svelte.dev/docs/cli/experimental.)

**Committing `.svelte-kit/` to git**, or treating it as source of truth instead of disposable build output. (Source: svelte.dev/docs/kit/project-structure.)

**Running `sv create` inside an existing project to "add" a feature** instead of `sv add` — `sv create` is for new projects only; `sv add` is the tool for evolving an existing one. (Source: svelte.dev/docs/cli/sv-create, svelte.dev/docs/cli/sv-add.)

**Never call `playground-link` after code is already written to a file.** The Svelte team's own AGENTS.md prompt is explicit: only offer a playground link after user confirmation, and "NEVER if code was written to files in their project." Calling it anyway needlessly exposes the code in a large, shareable URL. (Source: svelte.dev/docs/ai/instructions.)

**`create-svelte` is dead — don't generate anything that references it.** The current CLI docs (`cli/overview`, `cli/sv-create`) only describe `sv`; `create-svelte` does not appear anywhere in the live documentation tree, confirming it has been fully superseded. Any generated setup instructions or scripts calling `npm create svelte@latest` or `create-svelte` are targeting a retired tool. (Source: svelte.dev/docs/cli/overview, svelte.dev/docs/cli/sv-create — absence of any create-svelte reference.)

## AI and agent resources

Svelte publishes a first-party kit for coding agents, built from four pieces, all linked from [svelte.dev/docs/ai/overview](https://svelte.dev/docs/ai/overview): Instructions, the MCP Server, Skills, and Subagents. The pieces are meant to work together but each stands alone.

- **llms.txt docs bundles.** [svelte.dev/llms.txt](https://svelte.dev/llms.txt) is an index pointing to three sizes of the combined Svelte + SvelteKit docs — [llms-full.txt](https://svelte.dev/llms-full.txt) (everything, all examples), [llms-medium.txt](https://svelte.dev/llms-medium.txt), and [llms-small.txt](https://svelte.dev/llms-small.txt) — plus four package-scoped files: `/docs/svelte/llms.txt`, `/docs/kit/llms.txt`, `/docs/cli/llms.txt`, `/docs/ai/llms.txt`. An agent should pick the size that fits its context budget, or grab just the package it needs, before doing nontrivial Svelte/SvelteKit work.

- **Official Svelte MCP server** (`@sveltejs/mcp`). Run it locally with `npx -y @sveltejs/mcp` or point a client at the hosted version, `https://mcp.svelte.dev/mcp` (the Svelte team says it does not log, store, or inspect code sent there). It gives an agent four tools: `list-sections` (find relevant docs), `get-documentation` (fetch them), `svelte-autofixer` (statically checks generated Svelte code and reports issues/suggestions — call it in a loop until it comes back clean), and `playground-link` (only after the user confirms, and only if the code wasn't written straight to project files). It works with Claude Code, Claude Desktop, Codex CLI, Copilot CLI, Cursor, VS Code, Zed, OpenCode, and more, each documented individually — some get a single setup command, others (Claude Desktop, VS Code, Zed among them) walk through a multi-step GUI configuration instead. (Source: svelte.dev/docs/ai/local-setup.)

- **AGENTS.md / CLAUDE.md convention, or the plugin bundle.** Running `npx sv add ai-tools` now offers a choice: `ide`, `delivery` (`plugin` vs `tools`), `tools`, and — when `delivery:tools` includes `tools:mcp` — `mcpSetup` (`local` vs `remote`), which the CLI also stops to ask for interactively if it's left unset. For Claude Code or OpenCode, the recommended choice — `delivery:plugin` (no option here has a real default; the CLI always stops to ask unless every option is set explicitly) — installs the bundled Svelte Claude Code plugin — MCP server, skills, and subagents together, kept auto-updated, activated via a committed `.claude/settings.json` (trust-on-open, no `/plugin install` needed). Writing a plain AGENTS.md (or CLAUDE.md/GEMINI.md) with a ready-made agent-workflow prompt is what happens under the individual-tools path (`delivery:tools`) instead. The manual alternative to the add-on is `/plugin marketplace add sveltejs/ai-tools` followed by `/plugin install svelte`. Whichever path you take, keep the resulting file or plugin config current at the repo root — agents read it automatically. (Source: svelte.dev/docs/cli/ai-tools, svelte.dev/docs/ai/claude-plugin; `npx sv add --help` and `npx sv add ai-tools="ide:claude-code+delivery:tools+tools:mcp"` run on this machine.)

- **Official `svelte-file-editor` subagent.** Current docs describe this as a focused agent that can be invoked in parallel to execute atomic operations in a separate context window, so the main agent's context isn't spent on `.svelte` file edits. It's maintained in `sveltejs/ai-tools` and is one of the pieces installed by the `ai-tools` plugin bundle (or available individually under `delivery:tools`). Delegate `.svelte` file edits to it when your client supports subagents, rather than editing those files inline in the main agent. (Source: svelte.dev/docs/ai/overview, svelte.dev/docs/ai/subagent.)

- **Two official skills**, `svelte-code-writer` and `svelte-core-bestpractices`, installable into `.claude/skills` (or the Copilot/OpenCode equivalents). The first wraps the CLI doc/analysis tools and should load for any `.svelte` or `.svelte.ts/.svelte.js` file; the second covers Svelte 5 reactivity, events, and styling best practice for review and generation. Both are present and active in this environment.

- **CLI-only path.** The same three capabilities (`list-sections`, `get-documentation`, `svelte-autofixer`) are also callable as plain terminal subcommands of `@sveltejs/mcp`, for agents or scripts that don't speak MCP.

Everything above was fetched and confirmed directly from svelte.dev's own docs (and, for the MCP server and the two skills, cross-checked against the live connected tools in this session) — nothing here is a third-party wrapper.
