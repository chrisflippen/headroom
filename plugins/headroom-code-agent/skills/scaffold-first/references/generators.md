# generators scaffold-first reference (researched 2026-08-22, round 1)

This page covers two different jobs that both go by "generator." The first half is template/scaffolding **frameworks** — tools whose whole purpose is letting you define your own boilerplate and stamp it out repeatably: Hygen, Plop, Copier, Cookiecutter, and the generator side of Nx and Turborepo (Turborepo's generators are already covered end-to-end in `libraries-codegen.md`; this page only cross-references them). The second half is spec-to-code generation for event-driven APIs — the AsyncAPI Generator (`@asyncapi/cli`) — which is the async-messaging counterpart to the OpenAPI-side tools `libraries-codegen.md` already covers (openapi-typescript, Prisma); this page cross-references that content rather than repeating it. Every command below was run on this machine on 2026-08-22 with stdin closed (`< /dev/null`) unless noted otherwise — versions were resolved live from the npm registry and PyPI on the same date; re-check before trusting a specific number in a new session.

## Official setup commands

| Step | Command | What it generates |
|---|---|---|
| Bootstrap Hygen's own templates into a project | `npx hygen init self` | `_templates/` seeded with Hygen's own `generator/`, `init/repo/` starter templates |
| Scaffold a new Hygen generator | `npx hygen generator new <name>` | `_templates/<name>/new/*.ejs.t` — a starter template you edit by hand |
| Run a Hygen generator | `npx hygen <name> <action> [--name X] [data-flags...]` | whatever the `.ejs.t` frontmatter/body define; regenerating over an existing file prompts to overwrite unless `HYGEN_OVERWRITE=1` is set (see Traps) |
| Bootstrap a Plop project | `npx plop --init` (or `--init-ts` on Node 20.6+) | a starter `plopfile.js`/`.ts` with one empty generator — written in ESM syntax regardless of the project's module type (see Traps) |
| Run a Plop generator unattended | `npx plop <generator> -- --name X --type Y` (bypass by flag name) or `npx plop <generator> "value1" "value2"` (bypass by position — a real value for EVERY prompt; the docs' `_` placeholder deliberately leaves that prompt interactive and crashes a closed-stdin run with `ERR_USE_AFTER_CLOSE`, reproduced on this machine 2026-08-22, plop 4.0.5) | whatever that generator's `actions` array defines |
| Force-overwrite existing Plop output | add `-f`/`--force` | same output, skips the "already exists" confirmation |
| Bootstrap a Copier project, one-off | `uvx copier copy -f <template> <dest>` | files rendered from `<template>`'s Jinja tree; `-f` is shorthand for `--defaults --overwrite` |
| Bootstrap/run Copier as a pinned project dependency | `uv add --dev copier` once, then `uv run copier copy -f <template> <dest>` | same, using the version locked in `uv.lock` |
| Update an existing Copier-generated project | `uv run copier update -f` (or `uvx copier update -f` for a one-off) | diffs the template's newer version against `.copier-answers.yml` and merges — only works if that answers file exists (see Traps) |
| Bootstrap a Cookiecutter project, one-off | `uvx cookiecutter --no-input -o <dest> <template>` | files rendered from `<template>`'s Jinja tree, driven by `cookiecutter.json` |
| Bootstrap/run Cookiecutter as a pinned project dependency | `uv add --dev cookiecutter` once, then `uv run cookiecutter --no-input -o <dest> <template>` | same, version locked |
| Re-run Cookiecutter into a dir that already exists | add `-f`/`--overwrite-if-exists` | overwrites without prompting; omitted, the command exits `1` with `directory already exists` |
| Scaffold a new Nx workspace, fully unattended | `npx create-nx-workspace@latest <name> --preset=<preset> --interactive=false --nxCloud=skip --packageManager=<pm>` | full workspace skeleton (`nx.json`, package-manager workspace config) — also auto-wires Claude Code (`CLAUDE.md`, `.claude/settings.json`) out of the box, see AI and agent resources |
| Run an Nx generator, fully unattended | `npx nx g <plugin>:<generator> <name> [options] --interactive=false` | whatever that generator defines (a library, an app, a component…) |
| Preview an Nx generator without writing anything | add `-d`/`--dryRun` | prints the changes, writes nothing |
| Scaffold a local Nx plugin to hold custom generators | `npx nx g @nx/plugin:plugin <name>` | a plugin project; add generators inside it with `nx g @nx/plugin:generator` |
| Turborepo's own generators | — | see `libraries-codegen.md` — `turbo gen workspace` / `turbo gen run` cover Turborepo-specific package scaffolding and repo-custom Plop-style generators; not duplicated here |
| Scaffold a new AsyncAPI spec, fully unattended | `npx @asyncapi/cli new file --file-name <name>.yaml --example <example>.yaml --no-tty` | a starter AsyncAPI document seeded from one of the CLI's bundled examples |
| Validate an AsyncAPI document | `npx @asyncapi/cli validate <file>` | no files written; exits `1` on real errors, `0` when the only findings are info-level governance notices (e.g. "not on the latest spec version") |
| Generate typed models from a spec | `npx @asyncapi/cli generate models <language> <file> -o <dir> --no-interactive` | one class/interface file per schema, in the target language (`typescript`, `javascript`, `python`, `java`, `golang`, `csharp`, `kotlin`, `php`, `cplusplus`, `rust`, `scala`, `dart` are the full list of choices per `--help`) |
| Generate a baked-in protocol client from a spec | `npx @asyncapi/cli generate client <language> <file> -o <dir> --force-write` | a working pub/sub client skeleton — available for dart, java, javascript, python |
| Generate docs or code from a community template | `npx @asyncapi/cli generate fromTemplate <file> <template> -o <dir> --no-interactive --force-write` | whatever `<template>` defines — e.g. `@asyncapi/html-template` produces static HTML docs |

## Choosing

**Hygen vs. Plop for a project-local, hand-authored generator.** Both exist for the same job: you write the templates, the tool stamps them out. Hygen is convention-over-configuration — no config file, generators are just a folder structure (`_templates/<generator>/<action>/*.ejs.t`) — which makes it the faster tool to start with. Plop is config-over-convention — a single `plopfile.js` with a real JS API for prompts and actions — which makes it the more expressive tool once a generator needs conditional logic, custom action types, or answers computed from other answers. Plop is also the engine Turborepo's own `turbo gen` wraps (see `libraries-codegen.md`), so if the repo is already on Turborepo, `turbo gen` gets you Plop-style generators for free — don't add a bare `hygen` or `plop` dependency on top of it. Outside a Turborepo repo, pick Plop by default for the richer API and the documented (if slightly awkward) non-interactive bypass syntax; Hygen is fine for the simplest cases but carries two real footguns verified below (no CLI force flag, and its own quick-start template doesn't run).

**Copier vs. Cookiecutter for whole-project scaffolding.** Both render a Jinja-templated directory tree into a new project. Copier is the newer, more actively developed tool and its headline feature is `copier update` — it can re-apply a template's later changes onto a project that was already generated from it, merging via the recorded `.copier-answers.yml`. Cookiecutter has no equivalent: there is no `update` subcommand in its CLI at all (confirmed directly from `--help` — the only generation-related verbs are the one-shot run and `--replay`, which just re-plays your last answers, not the template's newer content). What Cookiecutter has instead is reach: its template ecosystem (cookiecutter-django, cookiecutter-pypackage, cookiecutter-data-science, and hundreds more) is larger and older than Copier's. Default to Copier for anything you intend to keep updating projects from over time; reach for Cookiecutter specifically when the template you want already exists in that ecosystem and Copier has no equivalent.

**Nx generators vs. Turborepo's `turbo gen` — pick by which monorepo tool you're already running.** These are not two options for the same repo; they're the generator system that ships with two different, competing monorepo tools. If the repo runs Nx, its generator system (`nx g`) is the richer of the two by a wide margin — a real plugin ecosystem (`@nx/react`, `@nx/js`, `@nx/plugin`, …) whose generators understand and update the workspace's project graph, plus first-class `--dryRun` and `--interactive=false` flags built into the core CLI rather than bolted on by each generator author. If the repo runs Turborepo, use `turbo gen` (see `libraries-codegen.md`) instead — don't introduce Nx's generator system into a Turborepo-run repo just for this.

**AsyncAPI Generator's place next to the OpenAPI tooling.** OpenAPI describes request/response REST APIs; AsyncAPI describes event-driven and async APIs (message queues, WebSockets, MQTT, Kafka topics) — a different problem, not a competing tool for the same one. A system with both a REST surface and an async surface needs both toolchains side by side; see `libraries-codegen.md` for the OpenAPI side (openapi-typescript, openapi-fetch). Within AsyncAPI's own generator, default to `generate models` when the goal is just typed payloads matching the spec's schemas — it's the closer analog to what openapi-typescript produces, except per-language rather than TypeScript-only. Reach for `generate client` only when you also want the actual pub/sub wiring (connect, subscribe, publish) generated, not just types, and `generate fromTemplate` when the target is something a baked-in mode doesn't cover — docs, a server skeleton, or any community/custom template.

## Never hand-write

Most of what these tools produce is *meant* to be hand-edited afterward — that's the entire point of a boilerplate generator, and it's the opposite case from the regenerate-only artifacts on `libraries-codegen.md`. The genuine exceptions:

- `.copier-answers.yml` — when a Copier template includes one, its own header says so explicitly: `# Changes here will be overwritten by Copier; NEVER EDIT MANUALLY`. Let `copier copy`/`copier update` write it; hand-editing it just gets silently overwritten (or worse, feeds `copier update` a false picture of what was actually answered).
- AsyncAPI `generate models` output — one class/interface per schema, meant to be regenerated whenever the spec's schema changes, the same category as Prisma's generated client or openapi-typescript's `.d.ts` (see `libraries-codegen.md`). Edit the spec, regenerate; don't hand-patch a generated model file.
- AsyncAPI `generate client` / `generate fromTemplate` output directories — same logic: regenerate from the spec and template rather than hand-patching the produced client or docs. `--force-write` exists precisely so this regeneration isn't blocked by "directory not empty."

Everything else — a fresh Hygen/Plop template's stamped-out files, a Copier/Cookiecutter project's initial file tree, an `nx g` generator's output (a library, a component) — is a starting point you're expected to keep editing. Don't try to keep it "in sync" with the generator the way you would a Prisma client.

## Thorough setup checklist

1. Right tool for the job picked deliberately: Hygen/Plop for a generator local to an existing repo, Copier/Cookiecutter for a whole new project, `nx g`/`turbo gen` only when that monorepo tool already runs the repo — not stacked on top of each other
2. Hygen/Plop bootstrapped with the tool's own init (`hygen init self` / `plop --init`), never a hand-typed `_templates/`/`plopfile.js` skeleton
3. If Plop: after `plop --init`, the scaffolded `plopfile.js` renamed to `.mjs` (or `"type": "module"` added to `package.json`) and re-run once before any real generator is written into it — the stock scaffold doesn't set this itself and the first real run against it fails to even load the file (see Traps)
4. Copier/Cookiecutter run through the uv spine: `uv add --dev` + `uv run` for a tool the project will invoke repeatedly, `uvx` reserved for genuine one-off project bootstraps
5. If Copier: confirmed the chosen template ships a `.copier-answers.yml.jinja` file before planning to rely on `copier update` later — without it there's nothing to update from (see Traps)
6. Nx workspace created with an explicit `--preset` and `--interactive=false` (or run inside an agent environment where the CLI auto-detects it), never a bare interactive `create-nx-workspace`
7. If Nx: `npx nx configure-ai-agents --agents <agent> --no-interactive` run once so the workspace's `AGENTS.md`/`CLAUDE.md`/MCP wiring is current for whichever coding agent is doing the work
8. AsyncAPI spec validated (`asyncapi validate <file>`, exit code checked, not just the printed summary) before any generation step runs against it
9. AsyncAPI generation wired to a real script/Makefile target keyed off the spec file (`generate models`, `generate client`, or `generate fromTemplate` as appropriate) — not run ad hoc from memory with hand-typed flags
10. Generated output is EXERCISED, not just generated: for a boilerplate framework this means actually running the stamped-out code once (see the Plop and AsyncAPI findings below — both regenerated their bespoke command's target and both showed why "the generator command exited 0" is not the same claim as "the output works"). Source: three recorded runs on this machine, 2026-08-22, in isolated scratch projects — not user repos. (1) A Plop-generated CommonJS component (`plop component -- --name Gadget`) was `require()`'d and called — printed `Gadget`, node exit `0`. (2) An Nx-generated library (`nx g @nx/js:library`) had its real test suite run (`nx test mylib`) — 1 test passed, exit `0`. (3) An AsyncAPI TypeScript model (`generate models typescript`) was imported the way its own default export actually requires and compiled with `tsc --strict` — exit `0`, then run with `node` and printed the expected values.

## Traps

**Hygen has no CLI flag to force-overwrite a regenerated file — the only lever is an environment variable, and it isn't in `--help`.** `hygen --help` lists exactly two options (`-h`/`--help`, `--dry`); there is no `--force`. Re-running a generator against a file that already exists drops into an interactive "Overwrite? (y/N)" prompt, and on closed stdin the prompt silently defaults to **N** — the command still exits `0`, but the file is left untouched. Reading the installed package's own source (`hygen/dist/ops/add.js`) shows the real mechanism: `if (!process.env.HYGEN_OVERWRITE && fileExists && !force)` — setting `HYGEN_OVERWRITE=1` (or a per-template `force: true` in the action's frontmatter) is the only way to bypass it unattended. (Source: `npx hygen --help` and two runs of `npx hygen mygen new` on this machine, 2026-08-22, hygen 6.2.11 — first without the env var left the pre-existing file unchanged at exit `0`, second with `HYGEN_OVERWRITE=1` overwrote it; confirmed by reading `add.js` in the installed package.)

**`hygen init self`'s own bundled example template renders JavaScript that doesn't run.** The stock `_templates/generator/new/hello.ejs.t` template — installed unmodified by `hygen init self`, then run with `hygen mygen new` after `hygen generator new mygen` — produces `const hello = \`\`\`...\`\`\`` followed by `console.log(hello)`. That's a syntax Hygen's own template author apparently intended as a multi-line string, but it isn't valid JS: running the generated file throws `TypeError: "" is not a function` and exits `1`. This only surfaces if you actually run the generated output — the generation step itself reports success. (Source: `npx hygen init self` then `npx hygen generator new mygen` then `npx hygen mygen new` then `node app/hello.js`, all run on this machine, 2026-08-22, hygen 6.2.11 — the last command exited `1` with the `TypeError` above.)

**A bare `plop <generator>` with an unanswered prompt doesn't skip or hang on closed stdin — it crashes.** Running `npx plop component < /dev/null` with no bypass flags hit an `inquirer` prompt, then threw `Error [ERR_USE_AFTER_CLOSE]: readline was closed` and exited `1` with a full stack trace — not a clean failure message, a crash. The documented bypass (`plop <generator> -- --name X` for named flags, or `_` positionally to skip a prompt) avoids the prompt entirely and completes normally. An agent driving Plop must always pass every prompt's answer this way; there is no single `--yes`/`--no-input` flag that accepts template defaults across the board. (Source: two runs of `npx plop component` on this machine, 2026-08-22, plop 4.0.5 — first with no bypass crashed with `ERR_USE_AFTER_CLOSE`, second with `-- --name Widget` completed with exit `0`.)

**`plop --init`'s own scaffolded `plopfile.js` uses ESM syntax without setting `"type": "module"` — and the first real generator run against it fails silently at exit `0`.** The file `--init` writes starts with `export default function (plop) {`. In a project whose `package.json` has no `"type": "module"` (the npm default), running any generator against that plopfile prints a Node "Failed to load the ES module" warning, then `[PLOP] Something went wrong with reading your plop file` and a `SyntaxError: Unexpected token 'export'` — but the process still **exits `0`**. An agent checking only the exit code would see success while no generator ever ran. The fix is either renaming the file to `.mjs` or adding `"type": "module"` to `package.json`; either one, re-run, completes normally. (Source: `npx plop --init` then `npx plop basics` on this machine, 2026-08-22, plop 4.0.5 — the run against the unmodified `plopfile.js` printed the SyntaxError above at exit `0`; renaming to `plopfile.mjs` and re-running produced clean output at exit `0`.)

**Copier's `.copier-answers.yml` is opt-in per template, not automatic — and `copier update` depends entirely on it existing.** Copier's own configuration docs are explicit that the template author must add a file named `{{ _copier_conf.answers_file }}.jinja` (typically `.copier-answers.yml.jinja`) to the template's root; if a template doesn't include one, no answers file is ever written, and `copier update` (or `check-update`) has no `_src_path`/`_commit` to work from later. This isn't a Copier bug — it's a template-authoring step that's easy to skip when building a template from scratch, and the failure only shows up much later, the first time someone tries to update a project generated from it. (Source: Copier's own configuring docs, https://copier.readthedocs.io/en/stable/configuring/#the-copier-answersyml-file — "The file must be called exactly `{{ _copier_conf.answers_file }}.jinja`… The file must have this content: `# Changes here will be overwritten by Copier; NEVER EDIT MANUALLY`"; confirmed by a run on this machine, 2026-08-22, copier 9.17.2, in which `copier copy` against a template without that file produced no `.copier-answers.yml` at all.)

**Cookiecutter has no update mechanism at all — don't reach for a flag that isn't there.** `cookiecutter --help` (2.7.1) lists no `update` verb; the only generation-related options are a fresh run and `--replay`/`--replay-file`, which replay *your own last answers*, not a newer version of the template's content. If a project needs to pick up a template's later changes, that's a job for Copier (`copier update`) or a third-party layer on top of Cookiecutter (e.g. `cruft`) — not a documented Cookiecutter feature. (Source: `uv run cookiecutter --help` run on this machine, 2026-08-22, cookiecutter 2.7.1.)

**AsyncAPI's TypeScript model generator defaults to a `class` with a default export — a plain named-import consumer won't compile.** `generate models typescript`'s own `--help` shows `--tsModelType` defaults to `class` (not `interface`) and `--tsExportType` defaults to `default` (not `named`). Writing `import { LightMeasuredPayload } from './models/LightMeasuredPayload'` against the generated file fails `tsc --strict` with `TS2614: Module has no exported member`; the correct consumption is `import LightMeasuredPayload from './models/LightMeasuredPayload'` plus `new LightMeasuredPayload({ ... })`, since every generated property is optional in the constructor's input type regardless of whether the source schema marks it required. This only surfaces when the generated model is actually imported and compiled, not when it's merely generated. (Source: `npx @asyncapi/cli generate models typescript --help`, and two `tsc --strict` runs against a generated model on this machine, 2026-08-22, `@asyncapi/cli` 6.0.2 — the named-import consumer failed with `TS2614` at exit `2`, the default-import consumer compiled at exit `0` and ran correctly with `node`.)

## AI and agent resources

**Nx has by far the deepest first-party agent integration of any tool on this page.** It ships an official `llms.txt` at `https://nx.dev/llms.txt`. It ships a real, official MCP server — `nx-mcp`, published from the `nrwl/nx-console` repo by Nx's own maintainers (confirmed via the npm registry's trusted-publisher metadata, not a third-party wrapper) — that gives an agent graph-aware workspace understanding, terminal-output access, and the ability to invoke generators directly. Beyond the MCP server, the CLI itself has a dedicated setup command, `npx nx configure-ai-agents --agents <agent> --no-interactive`, confirmed live on this machine: it generates `AGENTS.md`/`CLAUDE.md` and, for Claude Code specifically, registers an actual Claude Code plugin marketplace (`nrwl/nx-ai-agents-config`) inside `.claude/settings.json`. `create-nx-workspace` goes further still — its own `--help` output includes a worked example labeled "AI AGENTS (RECOMMENDED)" (`--template=empty --nxCloud=yes --interactive=false`), a dedicated `--aiAgents` flag, and documented auto-detection of `CLAUDECODE=1`/`OPENCODE=1` environment variables that switches the CLI into structured NDJSON progress output — all observed directly in a run on this machine, not just in docs. Treat the installed `AGENTS.md`/`CLAUDE.md` and the Nx MCP tools as more current than this page for anything Nx-specific, since `configure-ai-agents` updates them going forward.

**Copier and the AsyncAPI Generator both keep a repo-root `AGENTS.md`, but it's contributor-only guidance for patching the tool itself — the same caveat `libraries-codegen.md` already flags for Turborepo and knip.** `copier-org/copier`'s `AGENTS.md` documents Python-version targets, docstring style, and test conventions for people submitting PRs to Copier; `asyncapi/generator`'s `AGENTS.md` (the actual filename on GitHub — confusingly, the file's own internal heading says "AGENT.md") documents the monorepo's package topology and commit conventions for the same purpose. Neither is guidance for a project that merely depends on `copier` or `@asyncapi/generator`. Copier has no official `llms.txt` (`copier.readthedocs.io/llms.txt` and the `/en/stable/` variant both 404) and no official MCP server as of this check.

**Cookiecutter, Plop, and Hygen publish nothing official for agents as of this check.** No `llms.txt` on Cookiecutter's or Plop's docs domains (both checked, both 404), no repo-root `AGENTS.md` on `cookiecutter/cookiecutter` or `plopjs/plop` (checked their actual default branches — `main` for both), and no official MCP server for any of the three (npm/PyPI searches turned up only unrelated or clearly third-party packages — e.g. `@turbo/gen` and `node-plop` itself, not an MCP wrapper, for "plop mcp"). Hygen's docs domain (`hygen.io`) could not be reached from this machine at all — both a direct `curl` and a `WebFetch` request failed with TLS/HTTP2-level errors (`unable to get local issuer certificate` and a raw `HTTP/2 stream ... PROTOCOL_ERROR`) despite the server presenting what `openssl s_client` shows as a valid Let's Encrypt certificate for `*.hygen.io` — so Hygen's `llms.txt` status is genuinely **unverified**, not confirmed absent; its repo (`jondot/hygen`) has no `AGENTS.md` on its `master` branch, which was checked successfully via GitHub's raw-content host instead.

**The AsyncAPI organization has no official MCP server or agent-integration repo, and its own `llms.txt` is a confirmed 404.** Both `asyncapi.com/llms.txt` (which redirects to `www.asyncapi.com/llms.txt`) and the `www` host directly return 404. A scan of all 36 public repos under the `asyncapi` GitHub org turned up nothing MCP- or agent-named. The one MCP server that shows up searching npm for "asyncapi mcp" (`asyncapi-mcp-server`) is published by an individual maintainer from a personal repo, not the `asyncapi` org — don't present it as first-party. If an agent needs current AsyncAPI CLI/Generator detail beyond this page, fall back to Context7 or a direct docs fetch rather than assuming an official agent surface exists.
