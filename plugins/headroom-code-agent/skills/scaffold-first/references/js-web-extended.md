# js-web-extended scaffold-first reference (researched 2026-08-21, round 6)

Covers the three major JS/TS project creators not already in the standard: **Vue** (`create-vue`), **Nuxt** (`create-nuxt`), and **Expo** for mobile (`create-expo-app`). Do not use this page for SvelteKit, Next.js, or Astro — those have their own reference pages. Every command below was run live on this machine (macOS, Node v26.7.0, npm 11.19.0) with stdin closed (`< /dev/null`), so "what happens with no one there to answer a prompt" is observed behavior, not a guess.

## Official setup commands

| Step | Command | What it generates |
|---|---|---|
| Scaffold a Vue app | `npm create vue@latest -- <dir> [FEATURE_FLAGS...] [--force] [--bare]` | `package.json`, `index.html`, `src/` (main.ts, App.vue, components/, assets/), `public/`, `.gitignore`, `.editorconfig`, `.vscode/`, plus whichever config files the feature flags turn on (see table below) |
| See all Vue feature flags | `npm create vue@latest -- --help` | prints usage; no files written |
| Scaffold a Nuxt app | `npm create nuxt@latest -- <dir> --template <name> [--packageManager=<pm>] [--no-install] [--gitInit] [-M, --modules=<list>]` | `nuxt.config.ts`, `app/app.vue` (or `app.vue` at root on older templates), `public/`, `tsconfig.json`, `.gitignore`, `package.json` |
| Add a module to an existing Nuxt project | `npx nuxi module add <name> [--skipInstall] [--skipConfig] [--dev]` | installs the module package, appends it to the `modules` array in `nuxt.config.ts`, and runs any config the module ships (e.g. `@nuxt/eslint` writes `eslint.config.mjs`) |
| Scaffold an Expo app | `npx create-expo-app@latest <dir> [-t, --template <name>] [-y, --yes] [-e, --example <name>] [--no-install] [--no-agents-md]` | `app.json`, `App.tsx`/`App.js` or an `app/` router tree (template-dependent), `assets/`, `tsconfig.json` (TS templates), `package.json`, a git repo, and (new, see below) `AGENTS.md`, `CLAUDE.md`, `.claude/settings.json` |
| Add ESLint to an existing Expo project | `npx expo lint` | installs `eslint` + `eslint-config-expo`, writes `eslint.config.js`, adds a `"lint": "expo lint"` script to `package.json` — **see Traps, this needs to be run twice on a brand-new project** |

Verified package versions at time of writing (`npm view <pkg> version` and what npx actually installed, same numbers both ways): `create-vue@3.23.0`, `create-nuxt@3.37.0` (identical build to `nuxi@3.37.0` — `npm create nuxt@latest` and `npx nuxi init` run the exact same tool and print the exact same `--help`), `create-expo-app@4.0.0`. Resolve these fresh at the time you scaffold — `@latest` on all three, never a version typed from memory.

**Vue feature flags** (from the tool's own `--help`, confirmed by running it):

| Flag | Effect |
|---|---|
| `--default` | default config, no extras |
| `--ts`, `--typescript` | adds TypeScript |
| `--jsx` | adds JSX support |
| `--router`, `--vue-router` | adds Vue Router (SPA) |
| `--pinia` | adds Pinia |
| `--vitest` | adds Vitest |
| `--cypress` | adds Cypress E2E (adds Cypress Component Testing too if `--vitest` isn't also passed) |
| `--playwright` | adds Playwright E2E |
| `--eslint` | adds ESLint — **and always adds Oxlint alongside it, not optional** |
| `--prettier` | adds Prettier |
| `--oxfmt` | adds Oxfmt (Rust-based formatter) as an alternative to Prettier |
| `--vue-rc` | Pins Vue 3.6 Release Candidate instead of the stable release — works fine non-interactively despite the help text's interactive-sounding caveat (confirmed live: pins `"vue": "rc"`, exit 0 under closed stdin) |
| `--tests`, `--with-tests` (unstable) | shorthand for `--vitest --cypress` |
| `--eslint-with-prettier` (deprecated) | use `--eslint --prettier` instead |
| `--oxlint` (deprecated) | no-op now — Oxlint is bundled automatically whenever `--eslint` is chosen |

Observed: running `npm create vue@latest -- my-vue-app --typescript --router --pinia --vitest --eslint --prettier < /dev/null` completed non-interactively, exit 0, and produced `eslint.config.ts`, `.oxlintrc.json` (Oxlint config, even though `--oxlint` was never passed), `.prettierrc.json`, `vitest.config.ts`, `tsconfig*.json`, and a `package.json` with a `lint` script that runs both `oxlint` and `eslint` in sequence (`lint:oxlint` then `lint:eslint`) plus a `format` script (`prettier --write --experimental-cli src/`).

## Choosing

**`npm create vue@latest` vs `npm create nuxt@latest`.** Vue's own scaffolder (`create-vue`) gives you a client-rendered SPA with Vite — pick it when you're building a component-driven app that doesn't need server rendering, file-based routing, or a backend layer baked in. Nuxt is the full-stack meta-framework on top of Vue (SSR, file-based routing, server routes, auto-imports) — pick it when the project needs any of that, the same call as Next.js vs plain React. Don't default to Nuxt out of habit for something that's really just a SPA; the plain Vue scaffold is meaningfully lighter.

**Nuxt template: `minimal` vs `content` vs `ui` vs `module`.** `npm create nuxt@latest` (or `npx nuxi init`) requires `--template` when run non-interactively — confirmed by running it with stdin closed and no template: it fails with `Missing required argument: --template` and exit code 2. The available templates as of this check: `minimal` (a single `app.vue`, nothing else opinionated — the right default for most projects), `content` (content-driven site, wires `@nuxt/content`), `ui` (starts with Nuxt UI's component library and theme), `module` (scaffolds a Nuxt module, not an app), and `v5-nightly` (Nuxt 5 nightly channel — don't use it for anything that needs to ship). Pick `minimal` unless the project specifically wants Nuxt Content or Nuxt UI from day one.

**Nuxt's `minimal` template ships with no linting, formatting, or testing wired in.** Confirmed by inspecting the generated `package.json`: only `build`, `dev`, `generate`, `preview`, `postinstall`. Linting is a deliberate second step (`npx nuxi module add eslint`), not something the scaffold assumes you want. Don't skip that step just because the project "builds fine" without it.

**Adding tooling to Nuxt after scaffolding: use `nuxi module add`, not manual `npm install` + hand-edited `nuxt.config.ts`.** Confirmed by running `npx nuxi module add eslint < /dev/null`: it installed `@nuxt/eslint`, appended `'@nuxt/eslint'` to the `modules` array in `nuxt.config.ts` itself, and generated `eslint.config.mjs` — all with exit 0 and no prompt. Hand-installing the package and hand-editing the modules array works too, but skips whatever config-generation step the module ships (here, the `eslint.config.mjs` skeleton), so prefer the command.

**Vue has no equivalent "add tooling later" command.** Unlike Nuxt's `nuxi module add`, `create-vue`'s feature flags (`--eslint`, `--vitest`, etc.) are a creation-time decision only — there's no official "retrofit ESLint onto an existing Vue project" CLI. If a Vue project needs a tool it didn't start with, the closest to a scaffold-first path is running `npm create vue@latest -- --bare <flags-you-want>` in a scratch directory and copying the generated config files over, not hand-typing an ESLint flat config from memory.

**Expo template: `default` vs `blank` vs `blank-typescript` vs `tabs` vs `bare-minimum`.** Per Expo's own docs: `default` is multi-screen, ships Expo Router and TypeScript, and is the one Expo recommends for most new projects — it is versioned per SDK release; passing `--template default@sdk-<N>` pins a reproducible version for CI, but omitting the suffix does not hang or prompt under closed stdin — it silently resolves to the current SDK (confirmed live, exit 0, no prompt; current SDK is 57, confirmed by what `blank-typescript` actually installed: `expo@~57.0.15`). `blank` and `blank-typescript` are the un-routed minimal starts (no Expo Router, no navigation wired) — `blank-typescript` is the same thing with TypeScript already on. `tabs` wires Expo Router with a tab-navigation starting point and TypeScript. `bare-minimum` is `blank` plus a prebuild step that generates the native `android/` and `ios/` directories up front — reach for it only when the project needs native-module work from day one; every other template generates those directories on demand via `npx expo prebuild` (Expo calls this Continuous Native Generation — "ejecting" was removed in SDK 46 and no longer exists as a concept). Confirmed live: `blank`, `blank-typescript`, `tabs`, and `bare-minimum` scaffold without an SDK suffix and without prompting; only `default` needs the version pin.

**Expo's package-manager selection is implicit in the invocation, not a flag.** Per the CLI's own `--help` output: `npx create-expo-app` uses npm, `yarn create expo-app` uses Yarn, `pnpm create expo-app` uses pnpm, `bun create expo-app` uses Bun. There's no `--packageManager` flag the way Nuxt has one — the command you type is the choice.

**Linting for Expo: `npx expo lint`, not a hand-rolled ESLint flat config.** It installs `eslint` + `eslint-config-expo`, writes `eslint.config.js` extending `eslint-config-expo/flat`, and adds a `lint` script. Prettier is a separate, explicit step Expo's own docs describe: `npx expo install prettier eslint-config-prettier eslint-plugin-prettier --dev`, then wire `eslint-plugin-prettier/recommended` into `eslint.config.js` yourself (the plugin, not `eslint-config-prettier`, is what actually gets required in) — Expo does not generate a Prettier config file for you.

## Never hand-write

- Vue: `eslint.config.ts`, `.oxlintrc.json`, `.prettierrc.json`, `vitest.config.ts`, the `tsconfig*.json` set — all come from `create-vue`'s feature flags. There is no separate init command for any of these once the project exists (see Choosing above); regenerate via a scratch `create-vue` run rather than typing them from memory.
- Vue and Nuxt and Expo alike: `package-lock.json` — npm-managed, never hand-edited, exactly like `uv.lock` in the Python world.
- Nuxt: `nuxt.config.ts`'s `modules` array entries — added by `nuxi module add <name>`, not typed in by hand; everything else in that file (compatibility date, devtools flag, runtime config, your own app-specific settings) is normal to hand-edit.
- Nuxt: `eslint.config.mjs` — the skeleton (`import withNuxt from './.nuxt/eslint.config.mjs'`) comes from `nuxi module add eslint`; only the array you pass into `withNuxt(...)` is yours to fill in.
- Nuxt: the `.nuxt/` directory — fully generated by `nuxt prepare` / `nuxt dev`, git-ignored by the scaffold's own `.gitignore`, never touched by hand.
- Expo: `eslint.config.js` — the skeleton (`require("eslint-config-expo/flat")`) comes from `npx expo lint`'s first run; add rules on top, don't rewrite the `expoConfig` import.
- Expo: `tsconfig.json`'s `extends: "expo/tsconfig.base"` line — generated by the TypeScript templates; add `compilerOptions` overrides underneath it, don't replace the extends target.
- Expo: `AGENTS.md`, `CLAUDE.md`, `.claude/settings.json` — generated by `create-expo-app` itself (unless `--no-agents-md` was passed). `CLAUDE.md` is a one-line import (`@AGENTS.md`); put project-specific agent instructions in `AGENTS.md`, not in `CLAUDE.md`, so Claude Code and other agents that read `AGENTS.md` directly both see the same file.

## Thorough setup checklist

1. Decide Vue-SPA vs Nuxt before scaffolding — retrofitting one into the other later is a rewrite, not a config change.
2. Vue: run `npm create vue@latest -- <dir>` with every feature flag decided up front (TypeScript, router, Pinia, testing, ESLint, Prettier) — there's no official later-add path, so under-picking here means hand-wiring afterward.
3. Nuxt: run `npm create nuxt@latest -- <dir> --template minimal --packageManager npm --gitInit` (pin the template explicitly; it's a required argument non-interactively), then `npm install`.
4. Nuxt: `npx nuxi module add eslint` for linting — the scaffold ships with none.
5. Nuxt: add `@nuxt/test-utils` + Vitest by hand-installing (`npm i -D @nuxt/test-utils vitest @vue/test-utils happy-dom`) and writing a `vitest.config.ts` that uses `defineVitestProject` from `@nuxt/test-utils/config` — Nuxt has no `nuxi`-driven test scaffold as of this check.
6. Expo: pick the template deliberately (`default@sdk-<current>` for a routed app, `blank-typescript` for a bare TS start, `tabs` for tab navigation, `bare-minimum` only if native modules are needed immediately) and run `npx create-expo-app@latest <dir> --template <name>`.
7. Expo: `npm install` (or let the scaffold do it, i.e. don't pass `--no-install`), then run `npx expo lint` — and run it a **second time** if the first run errors (see Traps).
8. Expo: if Prettier is wanted, follow the two-step docs path (`npx expo install prettier eslint-config-prettier eslint-plugin-prettier --dev`, then wire it into `eslint.config.js`) — it is not bundled.
9. All three: run `npm run dev` (Vue/Nuxt) or `npm run ios`/`android`/`web` (Expo) once before writing feature code, to confirm the scaffold actually boots.
10. All three: commit the generated `.gitignore`/`package-lock.json` as-is; don't hand-edit either.
11. Expo: read the generated `AGENTS.md` — Expo writes a standing instruction there ("Expo HAS CHANGED... read the exact versioned docs...") specifically because SDK behavior shifts release to release; don't silently delete or ignore it.

## Traps

**`npx expo lint`'s first run on a brand-new project reports success and then crashes with exit code 1.** Reproduced twice on this machine on a fresh `blank-typescript` scaffold: the command prints "No ESLint config found. Configuring automatically," installs `eslint@^9.0.0` and `eslint-config-expo` via a subprocess `npm install`, writes `eslint.config.js`, adds the `lint` script to `package.json`, prints "ESLint has been configured 🎉" — and then throws `Error: Cannot find module 'eslint'` from `node_modules/expo/node_modules/@expo/cli/build/src/lint/lintAsync.js` and exits 1. The packages and config files it wrote are correct and complete on disk (verified with `ls node_modules/eslint` and `node -e "require.resolve('eslint')"` immediately after — both succeed). Running `npx expo lint` again immediately afterward succeeds silently with exit 0. The failure is a same-process module-resolution timing issue (the running Node process resolved its module paths before the just-installed `eslint` package existed on disk) — an agent that treats the first non-zero exit as "linting isn't set up" and gives up, rather than re-running the same command once, will wrongly conclude the project has no working lint step. (Recorded run: this session, 2026-08-21, `create-expo-app@4.0.0` / `expo@~57.0.15` on macOS, Node v26.7.0.)

**Nuxt's `npm create nuxt@latest` / `npx nuxi init` hangs waiting for a template choice if you don't pass `--template` — except it doesn't hang, it fails fast, which is easy to misdiagnose as "the tool is broken" instead of "a required flag is missing."** Reproduced: `npm create nuxt@latest -- my-app --packageManager=npm --no-install --gitInit=false < /dev/null` prints the full `--help` block, then `Non-interactive terminal detected. Missing required argument: --template`, and exits with code 2 (confirmed by checking `$?` directly, not through a pipe). An agent piping this through `| tail` or `| cat` will see a misleadingly-clean exit code from the pipe itself, not from `create-nuxt` — check the exit code of the actual command, not of a downstream pipe stage. Fix: always pass `-t`/`--template` (e.g. `minimal`) when scripting this. (Recorded run: this session, 2026-08-21, `create-nuxt@3.37.0`.)

**`--eslint-with-prettier` and `--oxlint` on `create-vue` are dead flags that silently do nothing harmful, but also nothing useful.** The tool's own `--help` lists both under "Deprecated feature flags" and says to use `--eslint --prettier` instead, and that Oxlint is now bundled automatically whenever `--eslint` is passed — confirmed by generation output: `.oxlintrc.json` and the `lint:oxlint` script appeared with only `--eslint` passed, no `--oxlint` flag given. An agent pattern-matching on an older Vue scaffolding guide (pre-Oxlint-bundling) that explicitly passes `--eslint-with-prettier` won't error, but will silently skip whatever migration behavior the newer combined flags have — pass `--eslint --prettier` instead. (Source: `npm create vue@latest -- --help`, `create-vue@3.23.0`, run on this machine.)

**`create-expo-app`'s `default` template is versioned per Expo SDK, but omitting `--template` (or passing it bare, `--template default`) does not hang or require the `@sdk-N` suffix under a closed stdin — it silently resolves to the current SDK.** Expo's own docs say the CLI "prompts which Expo SDK version to use" when `--template` is omitted (docs.expo.dev/more/create-expo.md) — that describes interactive (TTY) use. Live-tested here under closed stdin with `--no-install`: both `npx create-expo-app@latest <dir> --no-install < /dev/null` (no `--template` flag at all) and `npx create-expo-app@latest <dir> --template default --no-install < /dev/null` completed non-interactively with exit 0 and no prompt, pinning `expo@~57.0.15` — the same version an explicit `default@sdk-57` suffix would pin. So there is no reproduced non-interactive hang: the suffix is not required to avoid one. It's still good practice for scripted/CI use — it makes the target SDK explicit and reproducible instead of "whatever create-expo-app currently defaults to," and it's the only way to pin an *older* SDK than the current default. `blank`, `blank-typescript`, `tabs`, and `bare-minimum` never take an SDK suffix at all — confirmed live, `create-expo-app@latest my-expo-app --template blank-typescript --no-install < /dev/null` completed with exit 0 and no prompt. Don't guess the SDK number from training data — resolve it at scaffold time by checking what `expo` version a bare `default` scaffold actually pins (this session observed SDK 57: `expo@~57.0.15`, 2026-08-21, `create-expo-app@4.0.0`). (Source: https://docs.expo.dev/more/create-expo.md ["Without --template, create-expo-app prompts which Expo SDK version to use"], cross-checked against two live runs on this machine, closed stdin.)

## AI and agent resources

**All three ship a real `llms.txt`, confirmed by direct `curl` HTTP status checks (not WebFetch summarization, which can blur "the page mentions this" with "this file exists"):**
- Vue: `https://vuejs.org/llms.txt` (200, a table of contents) and `https://vuejs.org/llms-full.txt` (200, full docs). Individual guide pages are also available as clean markdown by appending `.md` to their path (e.g. `https://vuejs.org/guide/quick-start.md`).
- Nuxt: `https://nuxt.com/llms.txt` (200, ~5K-token overview) and `https://nuxt.com/llms-full.txt` (200, Nuxt's own docs describe it as "~1M+ tokens" — use the short one unless the agent's context window is 200K+ tokens). Individual pages are available as raw markdown at `https://nuxt.com/raw/docs/<version>/<path>.md`.
- Expo: `https://docs.expo.dev/llms.txt` (200) is unusual among the three — it opens with a dedicated "common misconceptions" section written specifically to correct stale LLM training data (e.g. "`expo eject` was removed in SDK 46 — it doesn't exist anymore," "`expo-cli` global install is deprecated, use `npx expo`"). There's also `https://docs.expo.dev/llms.md` (200, near-duplicate content). `https://docs.expo.dev/llms-full.txt` 301-redirects back to `/llms.txt` — no separate full-text variant exists, unlike Vue and Nuxt.

**Nuxt and Expo both ship an official documentation MCP server; Vue does not.**
- Nuxt: `https://nuxt.com/mcp` (streamable HTTP), confirmed official (built and hosted by the Nuxt team, described in their own blog post "Building an MCP Server for Nuxt"). Connect with `claude mcp add --transport http nuxt https://nuxt.com/mcp`. Exposes doc-page lookup, blog posts, deployment-provider instructions, module search, and changelog tools — general Nuxt knowledge, not project-specific. A companion module, `@nuxtjs/mcp-toolkit` — built by Hugo Richard (HugoRCD) under the `nuxt-modules` org, with Nuxt co-founder Sébastien Chopin (atinux) credited alongside him in Nuxt's own announcement post confirming it is the same tooling behind nuxt.com's own MCP server — lets *your own* Nuxt app expose custom MCP tools/resources/prompts via `npx nuxt add mcp`. Don't confuse the two: one is Nuxt's docs server (nuxt.com/mcp), the other is a way to add MCP serving to an app you're building, even though both trace back to the same team.
- Expo: `https://mcp.expo.dev/mcp` (streamable HTTP, OAuth), official. Connect with `claude mcp add --transport http expo https://mcp.expo.dev/mcp`. Exposes a few dozen tools and a prompt — the exact count drifts between checks, so consult the live list at https://docs.expo.dev/mcp/ rather than a pinned number — spanning documentation search, dependency install guidance, EAS build/CI-CD (`build_run`, `workflow_create`), TestFlight/App Store integration, and device automation (`automation_take_screenshot`, `automation_tap`) — expect this count to drift. Expo's own docs flag this tool list as "a reference and may not be up to date."
- Vue: no official MCP server as of this check — nothing on `vuejs.org` or in the Vue DevTools docs references MCP or agent integration. Don't invent one.

**Expo ships an official Claude Code plugin and generates agent-instruction files by default — this is new and worth knowing before scaffolding.** Confirmed by actually running `create-expo-app@latest` (no suppressing flag) and inspecting the output: the scaffold writes `AGENTS.md` (a short standing instruction to read version-pinned docs before writing code, since Expo SDK behavior changes release to release), `CLAUDE.md` (one line, `@AGENTS.md`, importing the former), and `.claude/settings.json` containing `{"enabledPlugins": {"expo@claude-plugins-official": true}}`. Expo's own docs confirm this is an officially maintained plugin, installable directly with `claude plugin install expo@claude-plugins-official`. Pass `--no-agents-md` to `create-expo-app` to skip generating all three files if the project has its own agent-config convention instead. Neither Vue's nor Nuxt's scaffolders generate anything analogous — no `AGENTS.md`, no plugin, no `.claude/` directory from either `create-vue` or `create-nuxt`.
