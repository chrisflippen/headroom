# libraries-codegen scaffold-first reference (researched 2026-08-21, round 6)

This page covers the widely-used JS/TS libraries whose whole point is to generate something — a types file, a mock file, a client, a config, or a new package — and where hand-editing the output defeats the tool. Versions below were resolved from the npm registry and from each CLI's own `--help`/`init` output on 2026-08-21; re-check before trusting them in a new session.

## Official setup commands

| Step | Command | What it generates |
|---|---|---|
| Generate types from an OpenAPI schema | `npx openapi-typescript ./schema.yaml -o ./schema.d.ts` (local file, remote URL, or JSON all work the same way) | a single `.d.ts` file with `paths`, `components`, `operations`, `webhooks` types, headed by `/** This file was auto-generated ... Do not make direct changes to the file. */` |
| Verify generated types aren't stale (CI/pre-commit gate) | `npx openapi-typescript ./schema.yaml -o ./schema.d.ts --check` | no file changes; exits `1` if the on-disk file doesn't match what would be generated right now, `0` if it does |
| Mock Service Worker install | `npx msw init ./public --save` | copies `mockServiceWorker.js` into the given directory; `--save` records the path as `msw.workerDirectory` in `package.json` so future `msw` upgrades know where to re-copy it |
| Prisma project bootstrap | `npx prisma init --datasource-provider postgresql` | `prisma/schema.prisma`, `prisma.config.ts`, `.env`, `.gitignore`, plus a best-effort `.claude/skills/`, `.agents/skills/`, `.windsurf/skills/`, and `skills-lock.json` (Prisma's own agent-skill bundle — pass `--no-skills` to suppress it) |
| Generate the Prisma Client | `npx prisma generate` | a typed client written to the path in `schema.prisma`'s `generator` block (`../generated/prisma` by default in current Prisma) |
| Create and apply a Prisma migration | `npx prisma migrate dev --name <message>` | a new folder in `prisma/migrations/` containing `migration.sql`, applies it to the dev database, regenerates the client |
| Storybook install, fully unattended | `npm create storybook@latest -- --yes --skip-install --type react --builder vite` (swap `--type`/`--builder` for your framework) | `.storybook/main.js`, `.storybook/preview.js` (or `.jsx`/`.ts` per framework), `storybook`/`build-storybook` scripts in `package.json` |
| Git hooks | `npx husky init` | `.husky/pre-commit` (starts as `npm test`) and adds `"prepare": "husky"` to `package.json`'s `scripts` |
| Knip config | `npm init @knip/config` | `knip.json` (schema-linked) plus a `knip` script added to `package.json` |
| Scaffold a brand-new monorepo | `npx create-turbo@latest` | full skeleton: `turbo.json`, `apps/`, `packages/`, workspace manifest (`pnpm-workspace.yaml` by default), starter `package.json` |
| Add a package/app to an existing turborepo | `turbo gen workspace --name <name> --empty --destination packages/<name> --type package`, **with an answer piped to stdin** (see Traps) | a new package directory with a template `package.json` and `README.md` |
| Run a repo's own custom generator | `turbo gen run <generator-name> --args <answers...>` | whatever that generator's own Plop-style templates in `turbo/generators/config.js` define — there is no built-in output; you write the generator first |

Plain libraries with no generator story, one line each: **openapi-fetch** (the runtime client paired with openapi-typescript's output — `npm install openapi-fetch`, then `createClient<paths>(...)` by hand, no CLI). **Tailwind CSS v4** — no `init` command exists any more; see Traps. **lint-staged** — config (`.lintstagedrc.json` or the `lint-staged` field in `package.json`) is always hand-written; there is no first-party generator (and the old community `npx mrm lint-staged` shortcut no longer scaffolds a bare config — see Traps).

## Choosing

**openapi-typescript is the right default.** It's actively maintained (7.13.0 as of this check), has no runtime dependencies in the generated output, and its `--check` flag gives you a real CI gate for drift — something the Java-based `openapi-generator-cli` and the older `swagger-typescript-api` don't offer in the same lightweight form. Don't churn off it; keep using `openapi-fetch` as the companion runtime client rather than hand-rolling `fetch` wrappers around the generated `paths` type — that's the whole reason the two projects are published as a pair.

**MSW: stick with the CLI-init worker, not a hand-copied one.** `msw init` copies a version-stamped `mockServiceWorker.js` whose integrity is checked against the installed `msw` package version at runtime (MSW warns on a version mismatch). Copying an old one from a tutorial or another repo produces exactly that warning. Current major is 2.x; if you find a 1.x-era snippet (`setupWorker` import paths, `rest.get` handler syntax) it predates the 2.0 rewrite (`http`/`graphql` handler syntax) and won't match today's API.

**Prisma vs. Drizzle for a new database client.** Prisma is the heavier, more batteries-included choice — `prisma init` scaffolds the project, `prisma migrate dev` diffs and applies schema changes, `prisma generate` produces a fully typed client, and (new since 7.x) it ships its own MCP server (`prisma mcp`) and a bundle of agent skills. Drizzle ORM is the lighter alternative: `drizzle-kit generate` and `drizzle-kit push` cover migrations, but there's no equivalent `init` that scaffolds a starter schema file — you hand-write the schema module from the start either way. Pick Prisma when you want the generated-client/migration workflow and don't mind vendoring `prisma.config.ts`; pick Drizzle when you want SQL-shaped, close-to-the-metal schema code and are fine owning migrations more directly. Neither is in this repo's dependencies today — this is a genuine choice, not an inherited one.

**Storybook builder: match whatever bundler the app already runs.** Storybook's Vite builder reuses an existing Vite config instead of standing up a second, separate Webpack pipeline — use `--builder vite` when the app runs Vite. Use `--builder webpack5` if the app runs Webpack, and `rsbuild` only after the app itself has moved to Rspack/Rsbuild.

**husky vs. simple-git-hooks / lefthook.** husky (9.1.7) has the widest adoption and the simplest single-command init. `simple-git-hooks` and `lefthook` both trade husky's `.husky/` directory-of-scripts model for a config-block-in-`package.json` (or a `lefthook.yml`) approach, which some teams prefer for readability — but neither offers a materially different init story.

**knip vs. depcheck / ts-prune.** knip is the more actively maintained, more complete tool of the three — it covers unused exports, unused dependencies, and unused files in one pass, where depcheck only covers dependencies and ts-prune only covers exports. No reason to add either alongside it.

**turbo's built-in generators vs. hand-rolled Plop.** `turbo gen` is Turborepo's own wrapper around Plop-style generators — reach for it (`turbo/generators/config.js` plus `turbo gen run`) instead of installing a bare `plop` dependency, since it's bundled with `turbo` and integrates with `turbo gen workspace` for the "new package" case out of the box.

## Never hand-write

- The `.d.ts` file openapi-typescript produces — regenerate it from the schema with `openapi-typescript ... -o ...`, never patch a type in place. The file says so itself in its header comment.
- `public/mockServiceWorker.js` — from `msw init`; it carries an embedded integrity check against your installed MSW version. Re-run `msw init` after upgrading `msw`, don't hand-edit the copied file.
- The Prisma generated client output (`generated/prisma/` or wherever the `generator` block in `schema.prisma` points) — entirely from `prisma generate`, never touched by hand.
- Files under `prisma/migrations/*/migration.sql` — from `prisma migrate dev --name ...`; hand-editing one after it's been applied anywhere just makes your migration history lie about what ran. (`schema.prisma` itself is the one Prisma file you're expected to hand-author on an ongoing basis — `prisma init` only scaffolds its first few lines.)
- `.storybook/main.js`/`preview.js` — the skeleton comes from `create-storybook`'s init; add addons and config inside them afterward rather than deleting and rewriting from memory. (Individual `*.stories.tsx` files are the opposite case — init only drops example stories as a starting template; every story after that is meant to be hand-written per component, that's the tool's job.)
- `.husky/pre-commit` and any other hook file under `.husky/` — the first one comes from `husky init`; edit the command inside it, don't recreate the file's boilerplate from memory.
- `knip.json`'s `$schema`-linked skeleton — from `npm init @knip/config`; add `workspaces`/`entry`/`ignore` patterns on top rather than writing the file from scratch.
- Anything under a freshly generated turborepo's `apps/`/`packages/` starter files, or a `turbo gen workspace` package's `package.json`/`README.md` — these come from `create-turbo` and `turbo gen workspace` templates; edit them after the fact, don't type the starter boilerplate from memory.

## Thorough setup checklist

1. `openapi-typescript` added as a dev dependency; a script (e.g. `"gen:api": "openapi-typescript ..."`) wired to the real schema source, not a stale local copy
2. A `--check` run wired into CI or a pre-commit hook so generated types can't silently drift from the schema
3. `msw init <publicDir> --save` run once per project so the worker directory is tracked in `package.json`, re-run after every `msw` upgrade
4. If there's a database: `prisma init` (or the Drizzle equivalent) run before any schema is hand-written; `prisma generate` run before the client is imported anywhere
5. Storybook installed with explicit `--type` and `--builder` flags, never bare `--yes` alone in an unattended run (see Traps)
6. `husky init` run, `.husky/pre-commit` populated with the real lint/test commands, hook installed and confirmed with a real commit
7. `npm init @knip/config` run, `knip.json` tuned to the repo's actual workspaces/entry points, `knip` passing (or has reviewed, intentional ignores)
8. `lint-staged` config hand-written (there's no generator) and wired into the husky `pre-commit` hook
9. turborepo tasks that consume generated files (`gen:api`, `prisma generate`, etc.) declared with the right `outputs` in `turbo.json` so Turborepo's cache doesn't skip regeneration when the schema changes
10. README documents the exact regeneration commands (schema → types, schema → client) so a clean clone can reproduce every generated file
11. Generated output is EXERCISED, not just generated: run the project's typecheck (or a small test that actually imports the generated types/client) and record its exit code — generation and drift-checks succeeding proves the output matches the schema, not that it is usable from real code. (Source: recorded test run on this machine, 2026-08-22, in an isolated scratch project — not a user repo: `npx openapi-typescript ./openapi.yaml -o ./src/generated/schema.d.ts` exit 0 (openapi-typescript 7.13.0, resolved live via `npm view`), then `npm run gen:api:check` with `--check` exit 0, yet the run's full command log contained no `tsc`, no test, and no import of the generated types — generation and drift-check both passed while nothing ever proved the output usable.)

## Traps

**`storybook@latest init --yes` alone still hits an interactive prompt and silently no-ops on closed stdin.** Directly observed on this machine: running `npx storybook@latest init --yes --skip-install --type react` with `/dev/null` as stdin printed a builder-selection prompt ("We were not able to detect the right builder for your project"), exited `0`, and wrote **zero files** — no `.storybook/` directory at all. Adding an explicit `--builder vite` (or `webpack5`/`rsbuild`) skips that prompt entirely and completes the install for real, confirmed by a second run that produced `.storybook/main.js` and `.storybook/preview.jsx`. Always pass `--type` and `--builder` together for an unattended run; `--yes` by itself is not the full non-interactive story. (Source: two runs of `npx storybook@latest init` on this machine, 2026-08-21, package version 10.5.10.)

**`turbo gen workspace` has no flag to skip its "add workspace dependencies?" prompt, and closed stdin makes it silently create nothing.** Every documented flag was passed (`--name`, `--empty`, `--destination`, `--type`) and the full `--help` output was checked for a suppressing flag — none exists. With stdin closed, the command exits `0` and creates no directory at all. Piping an explicit answer (`printf "n\n" | turbo gen workspace ...`) completes it and creates the package. An agent must feed stdin here, not just pass flags. (Source: two runs of `turbo gen workspace` on this machine, 2026-08-21, turbo 2.10.11 — first with `< /dev/null` produced no files, second piping `n\n` produced `packages/my-new-pkg2/package.json` and `README.md`.)

**Tailwind CSS v4 has no `init` command at all — not a deprecation, a removal.** `npx tailwindcss@latest init` fails before it even reaches Tailwind's own CLI, with npm's own "could not determine executable to run" (the bare `tailwindcss` package no longer ships a binary in v4). Installing the actual CLI package and asking it directly is worse, not better: `npx @tailwindcss/cli init` prints "Invalid command: init" and exits `1` — the v4 CLI's only subcommands are `build` and `canonicalize`. v4 is CSS-first: there is no `tailwind.config.js` to generate: config lives in the CSS file via `@import "tailwindcss"` and `@theme`. Don't invent an init command from v3-era memory. (Source: two runs on this machine, 2026-08-21, tailwindcss 4.3.3 — `npx tailwindcss@latest init` → npm error; `npx @tailwindcss/cli init` → "Invalid command: init", exit 1.)

**`msw init` does not have a `--no-save` flag, despite it circulating in summaries and some older blog posts.** The actual CLI help (`npx msw init --help`, msw 2.15.0) lists exactly four things: the `publicDir` positional, `--save`, `--cwd`, and the standard `--version`/`--help`. There is no `--no-save`. If you want the worker directory *not* recorded in `package.json`, the only lever is to simply omit `--save` — it isn't an opt-out flag, it's an opt-in one. (Source: `npx msw init --help` run on this machine, 2026-08-21.)

**`create-turbo@latest`'s `--skip-transforms` silently overrides `--package-manager`.** Passing both in the same invocation prints `>>> --skip-transforms conflicts with <package-manager>. The package manager argument will be ignored.` and the scaffold falls back to its own default (pnpm), not the one you asked for. If you need a specific package manager in the generated repo, don't pass `--skip-transforms` alongside it. (Source: `npx create-turbo@latest . --skip-install --skip-transforms --package-manager npm` run on this machine, 2026-08-21, printed the conflict warning and produced a pnpm-based repo.)

**`prisma init` writes agent-skill files into your repo by default — expected, but worth knowing about before it happens in CI.** As of Prisma 7.9.x, `prisma init` best-effort-installs a bundle of Prisma's own Claude/Windsurf/generic agent skills (`.claude/skills/`, `.windsurf/skills/`, `.agents/skills/`, `skills-lock.json` — nine skill folders, dozens of reference `.md` files) alongside the schema files, and does not fail initialization if that step fails. Pass `--no-skills` in CI or any environment where you don't want unreviewed third-party files landing in the tree from a single init command. (Source: `npx prisma@latest init` run on this machine, 2026-08-21, prisma 7.9.1 — confirmed by inspecting the generated `.agents/skills/prisma-cli/references/init.md`, which documents `--no-skills` itself.)

**Prisma blocks destructive commands from agent shells until it sees explicit consent text, and there's no way around it but the documented one.** `prisma migrate reset`, `prisma db push --force-reset`, and `prisma db push --accept-data-loss` are blocked when Prisma detects an AI-agent environment, until the exact user consent message is passed through `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION='<exact message>'`. The value must match what the user actually said, with no added quotes or newlines — don't fabricate it or reuse an old approval for a different action. The `prisma mcp` server deliberately has no `migrate-reset` tool at all, by design. (Source: Prisma's own `.agents/skills/prisma-cli/references/agent-safety.md`, generated by `prisma init` on this machine, 2026-08-21, citing the Prisma ORM 7.9.0 release.)

**The old `npx mrm lint-staged` shortcut no longer scaffolds a bare lint-staged config.** Some older tutorials use `mrm`'s `lint-staged` task to generate a starter config. Run today, it completes (`exit 0`) but refuses to do anything useful on its own: `Cannot add lint-staged: only eslint, stylelint, prettier or custom rules are supported` — it only works layered on top of one of those three tools' own mrm tasks, and along the way pulls in several packages (`inflight`, `rimraf@2`, `glob@7`, `osenv`, `libnpx`) that npm flags as long-deprecated. lint-staged's own README confirms there has never been a first-party `--init`: configuration is meant to be hand-written from the start. (Source: `npx mrm lint-staged` run on this machine, 2026-08-21.)

**openapi-typescript's `--check` only compares against the path given to `-o`.** Running `--check` without `-o` just prints the freshly generated types to stdout and exits `0` every time, regardless of whether an on-disk file is stale — it isn't comparing against anything. `-o` and `--check` have to be passed together for the drift check to mean anything. (Source: `openapi-typescript ./schema.yaml --check` run on this machine, 2026-08-21 — exited `0` with stdout output both before and after corrupting an unrelated file, because no `-o` path was given to compare against.)

## AI and agent resources

**Storybook** ships an official `llms.txt` at `https://storybook.js.org/llms.txt`, and its own CLI prints it in the completion message after `init` runs. More notably, a fresh Storybook install now detects when it's being run by a coding agent — the observed run on this machine printed `This command is running via an AI agent: claude-code_2-1-237_agent. Proceeding with agentic installation flow.` unprompted — and its completion output tells you to run `npx storybook ai setup` and follow its instructions, a dedicated command for wiring Storybook into an agent's toolset. Both were confirmed by direct runs on this machine, not just docs.

**Prisma** is the standout here: it publishes an official `llms.txt` at `https://www.prisma.io/docs/llms.txt`, ships a real MCP server started with `prisma mcp` (exposes schema/database context, `migrate-status`, `migrate-dev`, and Studio tooling to any MCP-aware client — deliberately not `migrate-reset`), and — new as of the 7.x line — `prisma init` installs nine skill folders of its own agent skills (CLI usage, client API, compute, driver-adapter implementation, database setup per provider, Postgres setup, MongoDB-upgrade guidance, and a v7 upgrade guide), plus a dedicated "agent safety" reference *inside* the CLI skill (not a tenth standalone skill) covering the destructive-command consent gate described above, directly into `.claude/skills/`, `.agents/skills/`, and `.windsurf/skills/`. This is a first-party, self-installing agent-resource bundle, not a third-party wrapper — treat the installed `SKILL.md`/`references/*.md` files as more current than this page for anything Prisma-CLI-specific, since they update every time `prisma init` runs again.

**Turborepo** publishes an official `llms.txt` at `https://turborepo.dev/llms.txt`, whose docs index opens by describing itself as "the build system for coding agents" and includes a dedicated AI-integration guide section. `vercel/turborepo` also keeps a real, current `AGENTS.md` at its repo root — but it's contributor-only guidance for people patching Turborepo itself (doc-update rules, no `--no-verify`, Rust lint conventions, PR title format), not guidance for projects that merely depend on `turbo`. There is no official Turborepo MCP server as of this check.

**knip DOES ship official agent tooling.** An official MCP server, `@knip/mcp`, is published by knip's own maintainer and documented on knip.dev's "Knip for Editors & Agents" post (December 2025), and the `webpro-nl/knip` repo carries a root `AGENTS.md` — contributor-only guidance for patching knip itself, the same caveat as Turborepo's, not guidance for downstream projects. `knip.dev/llms.txt` remains a genuine 404. (Source: npm view @knip/mcp, knip.dev/blog/for-editors-and-agents, raw.githubusercontent.com/webpro-nl/knip/main/AGENTS.md — all checked 2026-08-22.)

**openapi-typescript, msw, husky, lint-staged, and Tailwind CSS publish nothing official for agents as of this check.** No `llms.txt` on any of their docs domains (all checked, all 404: `openapi-ts.dev/llms.txt`, `mswjs.io/llms.txt`, `tailwindcss.com/llms.txt`), no repo-root `AGENTS.md` on `openapi-ts/openapi-typescript`, `mswjs/msw`, or `typicode/husky`, and no official MCP server for any of the five (re-verified 2026-08-22; only third-party wrappers exist). If an agent needs current API detail for these, fall back to Context7 or a direct docs fetch rather than assuming a first-party agent surface exists — don't invent one.
