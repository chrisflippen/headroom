# ml-pipelines scaffold-first reference (researched 2026-08-21, round 6)

## Official setup commands

| Step | Command | What it generates |
|---|---|---|
| New Kedro project | `uvx kedro new --name=<Name> --tools=<none\|lint\|test\|log\|docs\|data\|pyspark\|all> --example=<y\|n> --telemetry=<yes\|no>` | Project dir with `conf/base/{catalog.yml,parameters.yml}`, `conf/local/credentials.yml`, `src/<pkg>/{__init__.py,__main__.py,pipeline_registry.py,settings.py}`, `pyproject.toml` with `[tool.kedro]`, `requirements.txt`, `notebooks/` |
| New Kedro pipeline (inside a project, `kedro` already a project dep) | `uv run kedro pipeline create <name>` | `src/<pkg>/pipelines/<name>/{nodes.py,pipeline.py,__init__.py}`, `tests/pipelines/<name>/`, `conf/base/parameters_<name>.yml` |
| New ZenML repo | `uvx --from 'zenml[server]' zenml init` | `.zen/config.yaml` plus a local SQLite metadata store — bare `zenml` (no extra) crashes, see Traps |
| New ZenML repo from a project template | `uvx --from 'zenml[server,templates]' zenml init --template <e2e_batch\|nlp\|llm_finetuning\|starter> --template-with-defaults` | Pulls a copier template into the repo (pipelines, steps, `pyproject.toml`) — always stops for an email prompt first, see Traps |
| New DVC repo | `uvx dvc init [--subdir] [--no-scm]` | `.dvc/config`, `.dvc/.gitignore`, `.dvcignore` |
| Declare a DVC pipeline stage | `uv add --dev dvc` (one time, after `dvc init`), then `uv run dvc stage add -n <name> -d <dep> -o <out> [-p <params-key>] "<cmd>"` | Writes/updates the stage block in `dvc.yaml` |
| Run the DVC pipeline and lock it | `uv run dvc repro` | Writes/updates `dvc.lock` (exact command + content hashes) |
| New Dagster project | `uvx create-dagster@latest project <name> --no-uv-sync` (or `--uv-sync` to accept the sync) | `src/<name>/{__init__.py,definitions.py,defs/__init__.py}`, `tests/__init__.py`, `pyproject.toml` — `src/<name>/components/` isn't scaffolded until you run `dg scaffold component` |
| New MLflow experiment | `uv add mlflow`, then `uv run mlflow experiments create -n <name>` | A row in the local tracking store — as of MLflow 3, that's `sqlite:///mlflow.db` in the cwd by default, not the historical `./mlruns` file store, see Traps |
| MLflow project spec | Hand-write an `MLproject` YAML file at the repo root | No generator exists — MLflow's own docs only show example YAML, there's no `mlflow project init` |
| W&B run tracking | `wandb.init(project="<name>")` inside your training code, after `wandb login` or `WANDB_API_KEY` env var (or `wandb init [--project <p>] [--entity <e>] [--mode online\|offline\|disabled]` to write config first) | `wandb init` writes `wandb/settings` to the cwd but is a config initializer, not a source-tree generator like `kedro new`/`create-dagster project` — no src/, no pipeline files, no --template option, see Traps |
| Create a Hugging Face Hub repo | `uv run hf auth login` (or set `HF_TOKEN`), then `uv run hf repos create <namespace>/<name> [--repo-type model\|dataset\|space] [--private] [--exist-ok]` | A remote repo on the Hub — this is the closest thing HF ships to a scaffolder; there is no local file-tree generator |
| Install the HF CLI's agent skill | `uv run hf skills add --claude` (project-scoped) or `hf skills add --claude --global` | Writes the skill to `.agents/skills/hf-cli` (or `~/.agents/skills/hf-cli` with --global), and with --claude additionally symlinks `.claude/skills/hf-cli` to it so Claude Code picks it up |
| Add NeMo to a project | `uv add "nemo_toolkit[asr]"` (or `[tts]`, `[all]`, plus a CUDA extra like `[cu12]` — resolve live, see Choosing) | No project scaffold exists — NeMo is a library you import, not a generator |
| Add PyTorch (CPU or a specific CUDA build) | `uv add torch` for CPU/default, or configure `[[tool.uv.index]]` + `[tool.uv.sources]` for a CUDA build (see Choosing) — CUDA tag must be resolved live | Edits `pyproject.toml`/`uv.lock` only — no project scaffold exists for plain PyTorch |
| Add video decoding | `uv add torchcodec` (needs a matching `torch>=2.11`; use the same CUDA index as torch) | No scaffold — plain library |
| Add OpenCV | `uv add opencv-python-headless` for agents/servers/CI, or `uv add opencv-python` for a desktop GUI app — never both, see Traps | No scaffold — plain library |
| Install the notebook-output git filter | `uv run nbstripout --install [--attributes .gitattributes]` (after `uv add --dev nbstripout`) | Writes filter/diff config into `.git/config` and `.git/info/attributes` (or a versioned `.gitattributes` with `--attributes`) |
| Add the nbstripout pre-commit hook | Add a `repo: https://github.com/kynan/nbstripout` block (current release tag) to `.pre-commit-config.yaml`, then `uv run pre-commit install` | Standard pre-commit hook wiring |
| Pair a notebook with a plain-text file | `uv run jupytext --set-formats ipynb,py:percent <notebook>.ipynb` (after `uv add --dev jupytext`), or a `jupytext.toml` with `formats = "ipynb,py:percent"` to pair a whole directory | A paired `.py` file kept in sync with the `.ipynb` |
| Add the jupytext pre-commit hook | Add a `repo: https://github.com/jupytext/jupytext` block (current release tag) with `id: jupytext`, `args: [--sync]` to `.pre-commit-config.yaml`, then `uv run pre-commit install` | Enforces `.py`/`.ipynb` sync at commit time |

Every `uvx <tool> init`/`new`/`create` row above was actually run on this machine with stdin closed (`< /dev/null`) on 2026-08-21 to confirm real behavior — see Traps for the ones that didn't just work.

## Choosing

**Pick the orchestrator by what you're actually building, not by popularity.** **Kedro** (current: 1.5.0) is the right call for a data-science-shaped pipeline — a DAG of nodes reading/writing named datasets through its Data Catalog, with `catalog.yml`/`parameters.yml` as the contract. **Dagster** (current CLI: `create-dagster` 1.13.19) is the right call when the pipeline is one of several data assets in a broader production orchestration platform with scheduling, sensors, and a UI — it's a heavier, more ops-oriented tool than Kedro. **ZenML** (current: 0.96.3) sits in between: it's built specifically around MLOps concerns Kedro and Dagster don't natively have opinions on — swappable "stacks" (orchestrator, artifact store, experiment tracker, model registry) so the same pipeline code runs locally and on a cloud MLOps stack without rewriting it. Reach for ZenML specifically when stack-portability is the point; otherwise Kedro is the lower-ceremony default for a pure data/ML pipeline repo.

**Experiment tracking: MLflow vs Weights & Biases is a hosting-and-workflow decision, not a technical one.** MLflow (current: 3.15.1) is self-hostable, has no forced SaaS dependency, and its zero-config path just writes to a local file next to your code — pick it when you want to own the tracking store or avoid a third-party account. W&B is a hosted-first product (its CLI's `wandb init` is a config initializer that writes `wandb/settings` to the cwd, not a source-tree generator like `kedro new`/`create-dagster project` — tracking itself starts by calling `wandb.init()` in code) with a stronger out-of-the-box UI for comparing runs and sweeps — pick it when you want that UI and are fine with an external account and `WANDB_API_KEY`. Both now ship official MCP servers (see AI and agent resources), so "can an agent query my runs" is no longer a differentiator.

**Data/model versioning: DVC is still the default choice for this niche**, but note that its GitHub home changed — the CLI is now developed at `github.com/treeverse/dvc` (Treeverse, the company behind lakeFS), not `iterative/dvc`; `github.com/iterative/dvc` 301-redirects there today. This doesn't change any command, but don't cite the old org from memory.

**Notebook hygiene tools solve different problems — use both, not one or the other.** `nbstripout` strips output cells so diffs and git history don't fill up with base64 image blobs; it operates on the `.ipynb` file itself via a git filter or pre-commit hook. `jupytext` pairs a notebook with a plain-text `.py`/`.md` representation so code review and diffs happen on readable text instead of JSON; it doesn't touch output stripping. A repo with real notebook traffic wants nbstripout for clean diffs and jupytext if you also want notebooks to be reviewable as plain Python — they compose fine in the same `.pre-commit-config.yaml`.

**NeMo vs plain PyTorch (with or without Lightning): NeMo is the right call only when you're inside its target modalities.** NeMo (current: `nemo_toolkit` 3.0.0) is a full framework for ASR/TTS/LLM/multimodal training with pretrained recipes, not a general PyTorch scaffold — install only the extras you need (`[asr]`, `[tts]`, plus a CUDA extra like `[cu12]`/`[cu13]`; resolve which CUDA tag is current at install time, don't hardcode one). Outside NeMo's supported modalities, there is no official PyTorch project scaffolder at all — not from the PyTorch team, and not from Lightning AI either (the `lightning-hydra-template`/`lightning-template`/etc. projects on GitHub are all community-maintained, none is an official `pytorch.org` or `lightning.ai` product). For a plain PyTorch project, `uv init` + hand-laid-out `src/` is the expected, non-violating path — there's no generator to defer to.

**CUDA/torch index selection must be resolved live, not from memory or this page.** PyPI's stable CUDA tag for torch wheels has moved twice in recent releases — a newer CUDA became the stable default in one release and the older tag was deprecated in the following one (PyTorch dev-discuss release-packaging threads, fetched 2026-08-21) — so never assume any specific CUDA tag or torch version from memory or from this page. Before wiring a `[[tool.uv.index]]` CUDA index into a project, check `https://docs.astral.sh/uv/guides/integration/pytorch/` and `https://pytorch.org/get-started/locally/` for the current index tag, and match `torchcodec`'s index to whatever `torch` resolved to.

## Never hand-write

- `.zen/config.yaml` — from `zenml init`
- `dvc.lock` — fully machine-generated by `dvc repro`; DVC's own docs describe it as the file that records the exact command and content hashes that produced each stage's outputs
- `dvc.yaml` stage blocks — generated by `dvc stage add`; direct edits work but drift from the tool's own formatting, so prefer `dvc stage add`/`dvc stage remove` over hand-editing an existing stage
- `mlflow.db` (or `mlruns/**/meta.yaml` and run-artifact folders under the older file store) — written by the MLflow tracking client, never by hand
- `wandb/` run directories (`wandb/run-*`, `wandb/latest-run`) — written by `wandb.init()`
- Kedro's `pipeline_registry.py` and `settings.py` — Kedro's own docs say to keep these in their default `src/<pkg>/` location, generated by `kedro new`
- Kedro pipeline stub files under `src/<pkg>/pipelines/<name>/` and `tests/pipelines/<name>/` — from `kedro pipeline create`; `catalog.yml`/`parameters.yml`/`parameters_<name>.yml` are scaffolded stubs you're meant to fill in by hand, that part is expected
- Dagster's `.dg/telemetry.yaml` and any `$DAGSTER_HOME` instance storage (`runs.db`, event logs) — machine state, not source
- `uv.lock` — see `references/python-uv.md`; the same rule applies inside every ML project too
- Model weight/checkpoint files (`*.ckpt`, `*.pt`, `*.safetensors`, `*.onnx`) and any tracker-written sidecar metadata (e.g. an MLflow model directory's `MLmodel` file) — these are binary/generated artifacts; version them with DVC or an artifact store, not by hand-editing
- `.pre-commit-config.yaml` hook blocks for `nbstripout`/`jupytext` — copy the block from the tool's own README/docs (exact `repo:`/`rev:`/`args:`), don't retype one from memory

## Thorough setup checklist

1. `uv init` the project (see `references/python-uv.md` for the packaged/flat/lib/bare choice)
2. Pick and scaffold the orchestrator that fits (`kedro new`, `create-dagster project`, or `zenml init`) — don't default to whichever you used last time, see Choosing
3. `uv add` the ML libraries the project actually needs (`nemo_toolkit[...]`, `torch`, `torchcodec`, `opencv-python-headless`, etc.), resolving CUDA index tags live
4. `dvc init` if the project versions data or model artifacts, then declare the first pipeline stage with `dvc stage add` rather than hand-writing `dvc.yaml`
5. Wire experiment tracking — either point MLflow at a real tracking URI (don't leave it on the ambient sqlite default for a team project) or call `wandb.init()` with a real project name, and put the API key/URI in an env var, never in code
6. If the repo has notebooks: `nbstripout --install` (or the pre-commit hook) so outputs never land in git history, and pair notebooks with `jupytext --set-formats` if they're meant to be code-reviewed
7. `.gitignore` every machine-generated ML directory: `mlruns/`, `mlflow.db`, `wandb/`, `.dvc/cache`, `$DAGSTER_HOME` instance storage, model checkpoint dirs that aren't tracked by DVC
8. `.pre-commit-config.yaml` built from `pre-commit sample-config` plus the project's real hooks (ruff/pyrefly/pytest per `python-uv.md`, plus nbstripout/jupytext if notebooks exist), `pre-commit install` run
9. README documents the exact commands to rebuild the environment (`uv sync`), pull data (`dvc pull`), and reproduce the pipeline (`dvc repro`, `kedro run`, or `dagster dev`) from a clean clone

## Traps

**DVC's GitHub org moved from `iterative` to `treeverse` — training data almost certainly still says `iterative/dvc`.** Directly confirmed on this machine: `curl -sI https://github.com/iterative/dvc` returns `HTTP/2 301` with `location: https://github.com/treeverse/dvc`, and PyPI's own project metadata for the `dvc` package (checked 2026-08-21) lists `treeverse/dvc` as the source repo. No CLI command changes, but citing `iterative/dvc` as the current home, or filing/looking for issues there, is now wrong. (Source: direct `curl -I` redirect check and PyPI project page, both 2026-08-21.)

**`create-dagster project` prompts "Run uv sync?" and aborts on closed stdin — it doesn't hang, it fails.** Run directly on this machine: `uvx create-dagster@latest project dagtest < /dev/null` scaffolds the files successfully, then prints `A \`uv\` installation was detected. Run \`uv sync\`? ... (y/n) [y]: Aborted!` and exits 1 — an agent checking only the exit code will see failure even though the project files were written. Pass `--no-uv-sync` (or `--uv-sync` to accept it) to make the whole command exit 0 unattended; verified working directly. (Source: observed run, `create-dagster` version 1.13.19, 2026-08-21.)

**Bare `zenml init` (no package extra) crashes with `ModuleNotFoundError: No module named 'pymysql'` — not the `zenml[local]` ImportError message some ZenML docs/versions describe.** Run directly on this machine (fresh `uv cache clean zenml` + `uvx --refresh`, reproduced twice): `uvx zenml init < /dev/null` installs zenml, then crashes while initializing the SQL zen store with `ModuleNotFoundError: No module named 'pymysql'`, exit 1. The `zenml[templates]` extra alone produces the *identical* pymysql crash — it does not fail with a different message than the bare case. Using `uvx --from 'zenml[server]' zenml init` instead succeeds (exit 0) and creates `.zen/config.yaml`. You need `zenml[server,templates]` together to actually use `--template`. (Source: three observed runs, `zenml` 0.96.3, 2026-08-21.)

**`zenml init --template ... --template-with-defaults` still stops for an interactive email prompt, with no flag or env var found to suppress it.** Run directly with `zenml[server,templates]` installed: the command prints a ZenML welcome banner, asks `Email: ` ("leave blank to skip"), and aborts (exit 1) on closed stdin. Setting `ZENML_ANALYTICS_OPT_IN=false` first did not suppress the prompt (retested). `zenml init --help` lists only `--path`, `--template`, `--template-tag`, `--template-with-defaults` — no `--yes`/non-interactive flag exists. Note this prompt is specific to the *templated* init path — a bare `zenml init` (no `--template`) does not show it. Treat templated ZenML init as a human-attended command until ZenML ships a bypass. (Source: two observed runs, `zenml` 0.96.3, 2026-08-21.)

**MLflow's zero-config default tracking store changed from `./mlruns` to `sqlite:///mlflow.db` — older docs, tutorials, and training data still say `mlruns`.** Confirmed two ways: running `mlflow experiments create -n test` and separately calling `mlflow.start_run()` from Python in a fresh directory, both with no `MLFLOW_TRACKING_URI` set, produced `mlflow.db` in the cwd, and `mlflow.get_tracking_uri()` printed `sqlite:////.../mlflow.db`. MLflow's own current docs ("Tracking Experiments with Local Database") confirm this is the present default, and note the old `./mlruns` file store is only reused for backward compatibility if it already exists in the directory. Don't `.gitignore` only `mlruns/` — also ignore `mlflow.db`. (Source: two observed runs plus `https://mlflow.org/docs/latest/ml/tracking/tutorials/local-database/`, MLflow 3.15.1, 2026-08-21.)

**`opencv-python` and `opencv-python-headless` must never both be installed — the package's own README calls this out explicitly.** Both (and the `-contrib-` variants) install into the same `cv2` namespace with no plugin architecture, so having more than one in the environment silently produces broken/unpredictable behavior. The official guidance is: pick exactly one, and if you already have a conflict, `pip uninstall` all of them and reinstall one. (Source: `opencv-python` PyPI project page README, current version 5.0.0.93, checked 2026-08-21.) For agent/CI/container use, that one should be `opencv-python-headless` — the plain `opencv-python` package needs `libGL.so.1`, which headless Linux containers usually don't have, producing the well-known `ImportError: libGL.so.1: cannot open shared object file`. (Source: `opencv/opencv-python` GitHub issues #370, #851, #1019, checked 2026-08-21/22.)

**Don't conflate "NeMo" the training framework with "NeMo Agent Toolkit."** `nemo_toolkit` (the package used for ASR/TTS/LLM training, current version 3.0.0) has no official MCP server and no `llms.txt` — `docs.nvidia.com/nemo-framework/user-guide/latest/llms.txt` returns 404, directly checked. NVIDIA's separate **NeMo Agent Toolkit** project (`github.com/NVIDIA/NeMo-Agent-Toolkit`, the `nat` CLI, for building/orchestrating AI agents) does support MCP — it can run as an MCP server via `nat mcp serve` or a FastMCP runtime. These are two different NVIDIA products that happen to share the "NeMo" name; don't cite the Agent Toolkit's MCP support as if it applies to the model-training framework nemo_toolkit ships. (Source: direct 404 check on the NeMo Framework docs llms.txt path, plus `github.com/NVIDIA/NeMo-Agent-Toolkit` docs, 2026-08-21.)

**`wandb init` is real but it's a config initializer, not a project-tree scaffolder — don't expect it to lay out files like `kedro new` or `create-dagster project` do.** W&B's own CLI reference documents `wandb init [--project <p>] [--entity <e>] [--mode online|offline|disabled]`: "Initialize or update W&B configuration for the current directory. Set a project and entity, create local W&B settings, and prepare the directory for experiment tracking." Confirmed live on this machine: `uvx wandb init --project testproj --entity testent --mode offline < /dev/null` exits 0 non-interactively and writes a `wandb/settings` ini-style config file (`[default]` entity/project/mode) to the cwd. It has no `src/`, no pipeline files, and no `--template` option — actual run tracking still starts by calling `wandb.init(project="...")` inside your training code, with auth handled by `wandb login` or the `WANDB_API_KEY` env var. (Source: `https://docs.wandb.ai/models/ref/cli/wandb-init.md`, plus a live run of `uvx wandb init --project testproj --entity testent --mode offline < /dev/null`, both checked 2026-08-21.)

## AI and agent resources

**Kedro** publishes an official `llms.txt` at `https://docs.kedro.org/en/stable/llms.txt` (confirmed 200, live TOC content, checked 2026-08-21) and ships an official MCP server at `github.com/kedro-org/kedro-mcp` — "An MCP server to interact with components in Kedro" — confirmed via the GitHub API as owned by the `kedro-org` organization, not a community fork.

**ZenML** publishes both `https://docs.zenml.io/llms.txt` and a full-text `https://docs.zenml.io/llms-full.txt` (both confirmed 200), plus a live GitBook-hosted MCP endpoint at `https://docs.zenml.io/~gitbook/mcp` for querying docs in real time. Separately, ZenML ships an official MCP server for *operating* deployments (not just docs) at `github.com/zenml-io/mcp-zenml` — connect it from Claude Desktop/Cursor/etc. to query pipelines, runs, and stacks.

**DVC** has no official docs `llms.txt` and no official MCP server. `https://dvc.org/llms.txt` does return 200, but it's an auto-generated marketing-site index (built by a Yoast SEO WordPress plugin, literally says so in its own content) listing blog posts and top-level pages, not a documentation index — `https://doc.dvc.org/llms.txt` (the actual docs subdomain) 404s, directly checked. A GitHub API search of the `treeverse` org for MCP repos returned zero results; only unrelated community MCP wrappers (e.g. "wDVC MCP") exist. Don't cite DVC's marketing-site `llms.txt` as a documentation resource.

**Dagster** publishes an official `https://docs.dagster.io/llms.txt` (confirmed 200). The community package `dagster-mcp` (github.com/fabdendev/dagster-mcp) wraps the GraphQL API for run/asset/schedule/backfill management, but is NOT an official Dagster Labs project — the package's own README says so and points to the one actually-official server, the **Dagster+ MCP server** (`docs.dagster.io/guides/labs/dagster-mcp`), which exists for the hosted Dagster+ product specifically and is explicitly labeled preview/not-production-ready by Dagster's own docs.

**MLflow** publishes an official `https://mlflow.org/docs/latest/llms.txt` (confirmed 200) and ships an official MCP server as an install extra: `uv add 'mlflow[mcp]'` (requires MLflow ≥3.5.1) — "enables AI applications and coding assistants to interact with MLflow traces programmatically," per MLflow's own MCP docs page.

**Weights & Biases** publishes an official `https://docs.wandb.ai/llms.txt` (confirmed 200) and an official MCP server, `github.com/wandb/wandb-mcp-server` — graduated from preview to general availability in May 2026, hosted at `https://mcp.withwandb.com`, with one-command setup for Claude Code, Cursor, Codex, and Gemini CLI.

**Hugging Face** publishes official `llms.txt` files per docs surface (e.g. `https://huggingface.co/docs/hub/llms.txt`, confirmed 200) and runs an official MCP server at `https://huggingface.co/mcp` (source: `github.com/huggingface/hf-mcp-server`) exposing Hub search, Gradio Spaces, and more. Separately, the `hf` CLI (the modern replacement for `huggingface-cli`, renamed July 2025) ships its own agent-skill installer: `hf skills add --claude` writes an `hf-cli` Claude Code skill so an agent gets CLI usage context directly; the standalone installer script installs this skill automatically unless run with `--exclude-skill`.

**PyTorch** publishes an official docs `llms.txt` at `https://docs.pytorch.org/docs/stable/llms.txt` (confirmed 200) but has no official MCP server — only community projects (a PyTorch docs-search MCP, a PyTorch HUD MCP, a Lightning-specific MCP) exist, none under the `pytorch` or `pytorch-lightning` GitHub orgs.

**NeMo** (`nemo_toolkit`, the training framework) — no official `llms.txt` (404 confirmed at the obvious path) and no official MCP server. Do not confuse this with the separate NeMo Agent Toolkit project, which does support MCP but is a different product for agent orchestration, not model training — see Traps.

**opencv-python and torchcodec** are plain libraries with no agent-specific resources to note — nothing to fetch beyond their normal PyPI/GitHub pages.
